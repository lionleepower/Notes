# Python pathlib：用面向对象方式可靠地处理文件路径

`pathlib.Path` 把文件系统路径 (filesystem path) 抽象成对象，用 `/` 运算符拼接、用方法链解析，取代易错的字符串拼接和 `os.path` 嵌套调用。当脚本需要**跨平台**、需要**不依赖运行目录 (cwd) 就能定位文件**时几乎必用，核心咒语就是 `Path(__file__).resolve()`。

---

## 思路

不用它的问题：手动拼路径时你要处理分隔符 (`/` vs `\`)、重复斜杠、相对路径依赖 cwd 等一堆坑。`__file__` 给你的是**当前脚本自己的路径**，但它**可能是相对路径**——同一份代码，你从不同目录运行、或在 IDE 里运行，`__file__` 的值会不一样，直接拿去 `.parent` 找旁边的文件就可能算错。

它为什么适合：`Path` 是不可变 (immutable) 对象，拼接和取父目录都是纯字符串层面的操作，读起来像自然语言；`.resolve()` 则把路径**转成绝对路径**并解析掉 `..`、`.`、symlink 软链接，得到一个**稳定、唯一**的结果，不管你从哪运行都一致。

> [!tip]- 核心思路 「先把脚本自身路径变成可靠的绝对路径，再以它为锚点定位其他文件」。
> 
> ```python
> from pathlib import Path
> 
> # 当前脚本所在目录的绝对路径，作为一切资源定位的基准
> BASE_DIR = Path(__file__).resolve().parent
> config_path = BASE_DIR / "config.json"
> ```
> 
> 不变量：`BASE_DIR` 只依赖脚本文件的物理位置，与运行时的 cwd 无关。

## 1. 导入与创建

`Path` 必须从标准库 `pathlib` 导入，无需安装第三方包。创建路径对象有多种入口。

> [!success]- 基础语法
> 
> ```python
> from pathlib import Path
> 
> p = Path("data/config.json")   # 从字符串创建（相对路径）
> p = Path("/home/leyan/app")    # 绝对路径
> here = Path.cwd()              # 当前工作目录 current working directory
> home = Path.home()             # 用户家目录
> me = Path(__file__)            # 当前脚本文件自身的路径
> ```

---

## 2. 核心操作

|操作|作用|时间复杂度或注意事项|
|---|---|---|
|`p / "sub"`|拼接子路径，返回新 Path|$O(L)$ 纯字符串，不碰磁盘|
|`p.parent`|父目录|$O(L)$ 纯字符串，不碰磁盘|
|`p.name` / `p.stem` / `p.suffix`|文件全名 / 主干 / 扩展名|$O(L)$，如 `a.txt` → `a.txt` / `a` / `.txt`|
|`p.resolve()`|转绝对路径 + 解析 `..` 和 symlink|会访问文件系统（为解析 symlink）|
|`p.exists()` / `p.is_file()` / `p.is_dir()`|判断存在性与类型|有 I/O 开销，别在热循环里滥用|
|`p.iterdir()` / `p.glob("*.py")` / `p.rglob("*.py")`|列目录 / 通配 / 递归通配|I/O，返回惰性迭代器 (generator)|
|`p.read_text()` / `p.write_text()`|直接读写文本文件|I/O，省去 `open()` 样板|
|`p.mkdir(parents=True, exist_ok=True)`|创建目录（含多级父目录）|I/O，`exist_ok` 防重复报错|

> [!example]- 最小示例
> 
> ```python
> from pathlib import Path
> 
> p = Path("/home/leyan/project/main.py")
> print(p.name)     # main.py
> print(p.stem)     # main
> print(p.suffix)   # .py
> print(p.parent)   # /home/leyan/project
> print(p.parent / "utils.py")   # /home/leyan/project/utils.py
> ```

## 3. 关键行为与边界

最容易踩坑的是 `.resolve()`、`.absolute()`、`.parent` 三者「碰不碰磁盘」和「规不规范化」的差异，以及 `/` 拼接遇到绝对路径时的覆盖行为。

> [!tip]- 为什么这样做 `.resolve()` 会真正访问文件系统去跟踪 symlink，所以它返回的是「物理真实路径」；而 `.parent` 和 `/` 只做**字符串层面**的运算，不验证路径是否存在。这解释了为什么 `Path("a/../b").parent` 得到的是 `a/..` 而不是你直觉里的根目录——它没有做规范化。

> [!warning]- 边界条件
> 
> - `.resolve()` vs `.absolute()`：前者解析 `..` 和 symlink 并规范化；后者只在前面拼上 cwd，**不**消除 `..`。定位脚本资源要用 `.resolve()`。
> - `__file__` 的相对/绝对形态**不保证**，取决于运行方式和 Python 版本，所以永远显式 `.resolve()`，别裸用。
> - `/` 拼接时若**右侧是绝对路径**，会直接覆盖左侧：`Path("/a") / "/b"` 结果是 `/b`，不是 `/a/b`。
> - `.parent` 到达根目录后再取父目录仍是根本身（`Path("/").parent` 还是 `/`），不会报错也不会越界。

## 4. 实例一：定位脚本旁边的资源文件

输入：一个和脚本放在同一目录的 `config.json`；目标：无论从哪个目录运行脚本都能正确读到它。这是 `Path(__file__).resolve()` 最经典的使用动机。

> [!success]- 完整实现
> 
> ```python
> from pathlib import Path
> import json
> 
> 
> def load_config():
>     # 脚本所在目录的绝对路径，作为锚点
>     base_dir = Path(__file__).resolve().parent
>     config_path = base_dir / "config.json"
> 
>     if not config_path.exists():
>         raise FileNotFoundError(f"缺少配置文件：{config_path}")
> 
>     return json.loads(config_path.read_text(encoding="utf-8"))
> 
> 
> print(load_config())
> ```

主流程：先用 `Path(__file__).resolve().parent` 求出稳定锚点 `base_dir`，再用 `/` 拼出目标文件。最容易写错的位置是**漏掉 `.resolve()`**——一旦用 `python ../other/main.py` 这类方式运行，`base_dir` 就会算歪，`config.json` 便找不到。

## 5. 实例二：遍历项目目录，批量收集文件

输入：一个项目根目录；目标：递归找出所有 `.py` 文件并统计行数。这体现了 `pathlib` 在「实战脚本」里替代 `os.walk` 的价值——用 `rglob` 一行搞定递归通配。

> [!success]- 完整实现
> 
> ```python
> from pathlib import Path
> 
> 
> def count_lines(root):
>     root = Path(root).resolve()
>     total = 0
>     for py_file in root.rglob("*.py"):
>         # rglob 递归匹配所有子目录下的 .py 文件
>         lines = len(py_file.read_text(encoding="utf-8").splitlines())
>         print(f"{py_file.relative_to(root)}: {lines} 行")
>         total += lines
>     return total
> 
> 
> print(f"总计 {count_lines('.')} 行")
> ```

> [!summary]- 当前实例复杂度
> 
> - 时间复杂度：$O(N + \sum L_i)$，$N$ 为目录树中文件总数（遍历成本），$L_i$ 为各文件字节数（读取成本），主导项通常是 I/O 而非计算。
> - 空间复杂度：$O(M)$，`rglob` 返回惰性迭代器不占额外空间，但 `read_text` 会把单个文件整体载入内存，$M$ 为**当前**文件大小；不会同时驻留所有文件。

## 6. 与相近写法怎么选

|需求|推荐写法|原因|
|---|---|---|
|新代码里做路径拼接/操作|`pathlib.Path`|面向对象、跨平台、可读性强，Python 官方推荐|
|维护大量旧 `os.path` 代码|保持 `os.path`|混用会降低一致性；`os.path` 仍完全可用|
|需要绝对路径 + 解析 symlink|`.resolve()`|`.absolute()` 不消除 `..`、不跟踪 symlink|
|只想在字符串前拼 cwd、不访问磁盘|`.absolute()`|`.resolve()` 会碰文件系统，纯拼接场景没必要|
|拼一段路径|`p / "a" / "b"`|比 `p.joinpath("a", "b")` 更直观；两者等价|

## 7. 常见易错点

> [!warning]- 易错点
> 
> - 裸用 `Path(__file__).parent`：不 `.resolve()` 时，相对形态的 `__file__` 会让父目录算错，正确写法始终是 `Path(__file__).resolve().parent`。
> - `/` 拼接放错顺序：把绝对路径放右边会覆盖左边（`Path("/a") / "/b"` → `/b`），拼子路径时右侧务必用相对片段。
> - 在循环里反复 `.exists()` / `.is_file()`：每次都有 I/O 开销，能缓存结果就别重复调用。
> - 忘记 `encoding`：`read_text()` / `write_text()` 默认编码依赖平台，处理中文文本时显式写 `encoding="utf-8"` 更稳。
> - 误以为 `.parent` 会规范化：它是纯字符串运算，`Path("a/../b").parent` 不等于你直觉里的结果，需要规范化就先 `.resolve()`。

---

## 复杂度

> [!summary]- 复杂度
> 
> - 核心操作（拼接、取父目录、取名字）：时间复杂度 $O(L)$，$L$ 为路径字符串长度，纯内存运算，不访问磁盘。
> - `.resolve()`：除字符串处理外还需跟踪 symlink，含**文件系统 I/O**，实际耗时由磁盘决定而非路径长度。
> - `glob` / `rglob` / `iterdir`：$O(N)$，$N$ 为被遍历的目录项数量，且返回惰性迭代器，额外空间 $O(1)$（不含你自己收集的结果）。

---

## 一句话总结

`pathlib.Path` 是「面向对象的跨平台路径工具」，看到需要跨平台或不依赖 cwd 定位文件的信号就用它，最关键写法是 `Path(__file__).resolve().parent` 求出脚本锚点、再用 `/` 拼出目标路径。

## 模板归纳

看到以下信号时，优先想到 `pathlib`：

- 需要「脚本旁边的资源文件」——配置、数据、模板，且要求换目录运行也能找到。
- 需要跨平台路径拼接，不想手动处理 `/` 与 `\`。
- 需要遍历目录、按通配符批量收集文件（`glob` / `rglob`）。

```python
# 可直接复用的最小模板：脚本锚点 + 资源定位
from pathlib import Path


def resource_path(*parts):
    base_dir = Path(__file__).resolve().parent
    return base_dir.joinpath(*parts)


# 用法：resource_path("data", "config.json") → 脚本目录下 data/config.json 的绝对路径
```
