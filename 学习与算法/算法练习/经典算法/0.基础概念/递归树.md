# 递归树：树是画出来的，执行是一条线

递归树 (Recursion Tree) 把每层递归的所有分支画成一棵树，用来看清回溯 / 分治的枚举全貌。它解决的问题：递归代码只有几行，却看不出「到底枚举了什么」；画出树，枚举结构一目了然。

---

## 思路

不画树时，人会本能地在脑子里跟踪整条执行轨迹——层数一多必然爆炸。递归树把「结构」和「执行」分开：结构用树看，执行只信任「每个节点只做自己那一步，剩下交给递归」。

> [!tip]- 核心思路
> 
> 一棵递归树里只有两个方向：
> 
> - **for 循环 = 横向**：同一位置换不同候选（兄弟节点）。
> - **递归调用 = 纵向**：推进到下一个位置（父 → 子）。
> 
> 回溯代码的抽象感往往来自两者混在一起，分开看就清楚了。

---

## 1. 树是画出来的，执行是一条线

递归树最容易骗人的地方：几条分支并排画着，看起来像「同时」在跑，好像 `path[0]` 同时是 `a`、`b`、`c`。但代码是单线程的，for 一次只跑一个迭代。

> [!example]- 时间轴 vs 树
> 
> ```python
> for c in "abc":
>     path[0] = c
>     dfs(1)     # 这一行必须整棵子树跑完才返回，才进下一次循环
> ```
> 
> 时间轴上实际是：
> 
> ```text
> path[0]='a' → a 开头的答案全收完 → path[0]='b' → b 开头的全收完 → …
> ```
> 
> 任何一个瞬间，`path` 里只有一份值——「当前正在走的这条路径」。**没有条件竞争，因为没有「同时」，只有「先后」。**

关键机制：`dfs(i+1)` 是**阻塞的同步调用**，跟 `print()` 一样，调用方停在原地等它返回。所谓「递归怎么知道要回去」——不需要知道：函数 return 后，代码自然接着执行 for 的下一次迭代。

---

## 2. 读树的三个对应关系

| 树上的元素 | 对应代码 | 含义 |
| --- | --- | --- |
| 节点 | 一次 `dfs(i)` 调用 | 一个子问题 |
| 兄弟分叉 | for 的一次迭代 | 同一位置的不同候选 |
| 父子边 | `dfs(i+1)` | 当前决定做完，推进下一位 |

答案在哪里由题型决定：只有完整方案合法 → 叶子是答案；构造过程每步都合法（如子集）→ 每个节点都是答案。对照见 [[6.1 子集型回溯]]。

---

## 3. 实例：digits = "23" 的递归树

> [!example]- 完整的树
> 
> ```text
>                  dfs(0)  path=['','']
>          ┌──────────┼──────────┐
>        a           b           c        ← for 横向（兄弟）
>       dfs(1)      dfs(1)      dfs(1)    ← 递归纵向（父→子）
>      ┌──┼──┐     ┌──┼──┐     ┌──┼──┐
>      d  e  f     d  e  f     d  e  f
>      ↓
>    9 个叶子，每个叶子收一份答案
> ```
> 
> 真实执行顺序是深度优先 DFS 的一条线：`ad → ae → af → bd → …`，先把 a 子树全部走完，才轮到 b。

## 常见易错点

> [!warning]- 易错点
> 
> - **把树当并发**：以为几条分支同时持有不同的 `path[0]`——实际所有分支共享同一个 `path`，靠先后覆盖 / 恢复轮流使用，见 [[状态恢复]]。
> - **想同时跟踪整条执行轨迹**：必然爆炸。正确姿势是只写「任意一个抽象节点」的通用规则，剩下交给数学归纳法。
> - **用树深估时间复杂度**：时间复杂度按「节点 / 叶子总数 × 单点代价」估算，树深只决定空间（递归栈）。

---

## 一句话总结

递归树横向是 for、纵向是递归；树画的是所有可能，执行永远是深度优先的一条线，任何瞬间只存在一条路径。

---

## 模板归纳

看到以下信号时，先画递归树：

- 回溯代码看不出枚举了什么 → 画树看结构
- 怀疑方案有重复 / 遗漏 → 数叶子对不对得上
- 估复杂度 → 节点（叶子）数 × 单点代价
