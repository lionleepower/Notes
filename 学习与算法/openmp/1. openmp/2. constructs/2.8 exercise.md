
# OpenMP Exercises

## 1. 本节核心总结

这一节不是介绍新的 OpenMP construct，而是通过几个小练习帮助你实际使用 OpenMP，包括：

1. 编译并运行 OpenMP 程序。
2. 使用 `OMP_NUM_THREADS` 控制线程数量。
3. 观察 parallel region 中的线程行为。
4. 测试 worksharing loop 的性能。
5. 比较手写 OpenMP 代码和高性能数学库的性能差异。

简单理解：

| Exercise | 核心目的 | 主要文件 |
|---|---|---|
| Setup | 配置环境、下载代码、选择 Makefile | `Makefile` |
| OMP Hello World | 观察 OpenMP 线程 ID | `hello.c`, `hello.f90` |
| Worksharing Loop | 测试循环并行性能 | `daxpy.c`, `daxpy.f90` |
| OMP Functions | 使用 OpenMP 函数和计时 | `work.c`, `work.f90` |
| Serial vs OpenMP | 比较串行和单线程 OpenMP 开销 | `work_serial.c`, `work_serial.f90` |
| Hand-coding vs Library | 比较手写 DAXPY 和 BLAS 库 DAXPY | `daxpy2.c`, `daxpy2.f90` |

一句话记忆：

> 这一节的重点是从“会写 OpenMP 指令”过渡到“会编译、运行、测性能、比较结果”。

## 4. 为什么建议使用 dedicated node？

课本提到，部分练习涉及性能测量，所以最好在专用计算节点上运行，而不是在 login node 上跑。

原因：

|运行位置|适合做什么|不适合做什么|
|---|---|---|
|Login node|编辑代码、编译、小测试|长时间运行、性能测试|
|Dedicated compute node|正式运行、性能测量|普通登录交互|

可以通过 interactive job 获取一个专用节点：

```bash
idev -p development -A <allocation> -t 0:30:00 -n 1 -N 1
```

等价于：

```bash
srun -p development -A <allocation> -t 0:30:00 -n 1 -N 1 --pty /bin/bash -l
```

这里的重点是：

> 性能测试应该尽量在独占或相对稳定的计算节点上运行，否则结果可能受其他用户进程影响。

# Exercise 1: OMP Hello World

## 7. 练习目标

第一个练习是 OpenMP 的 Hello World。

主要目的：

1. 确认 OpenMP 程序能正确编译。
    
2. 观察 parallel region 中多个线程是否被创建。
    
3. 理解 thread ID 的含义。
    
4. 学会用 `OMP_NUM_THREADS` 控制线程数量。
    

相关文件：

```text
hello.c
hello.f90
```

---

## 8. 编译和运行 Hello World

编译：

```bash
make hello
```

设置线程数为 3：

```bash
export OMP_NUM_THREADS=3
```

运行：

```bash
./hello
```

也可以使用 Makefile 提供的目标：

```bash
make run_hello
```

---

## 9. OMP_NUM_THREADS 是什么？

`OMP_NUM_THREADS` 是一个环境变量，用来告诉 OpenMP 程序默认使用多少个线程。

例如：

```bash
export OMP_NUM_THREADS=4
./hello
```

表示程序进入 parallel region 时，默认尝试使用 4 个线程。

注意：

> `OMP_NUM_THREADS` 不是编译选项，而是运行时控制参数。

---

## 10. Hello World 练习应该观察什么？

假设程序输出类似：

```text
Hello from thread 0
Hello from thread 1
Hello from thread 2
```

说明：

|现象|含义|
|---|---|
|输出多个 thread ID|parallel region 创建了多个线程|
|输出顺序不固定|多线程执行顺序不确定|
|thread ID 从 0 开始|OpenMP 通常用 0 表示 master thread|
|每次输出顺序可能不同|调度由 runtime 决定|

重要理解：

> 并行程序的输出顺序通常不能直接依赖，因为多个线程可能同时执行。

# Exercise 2: Worksharing Loop

## 11. 练习目标

第二个练习使用 `daxpy.c` 或 `daxpy.f90`，测试 worksharing loop 的并行性能。

相关文件：

```text
daxpy.c
daxpy.f90
```

它执行的是 DAXPY 类型操作：

```text
y = a*x + y
```

其中：

|名称|含义|
|---|---|
|`DAXPY`|Double-precision A X Plus Y|
|`a`|标量 scalar|
|`x`|向量 vector|
|`y`|向量 vector|
|`N`|向量大小|

---

## 12. DAXPY 是什么？

DAXPY 是线性代数中的经典操作：

```text
y[i] = a * x[i] + y[i]
```

如果写成循环：

```c
for (int i = 0; i < N; i++) {
    y[i] = a * x[i] + y[i];
}
```

这个循环每个 iteration 通常相互独立，所以很适合使用 OpenMP `parallel for` 并行化。

---

## 13. 编译和运行 DAXPY

编译：

```bash
make daxpy
```

设置线程数：

```bash
export OMP_NUM_THREADS=3
```

运行：

```bash
./daxpy
```

或者：

```bash
make run_daxpy
```

---

## 14. 为什么 DAXPY 要重复执行十次？

课本提到，DAXPY 操作会重复执行十次，用来收集性能统计数据。

原因是：

|原因|解释|
|---|---|
|单次运行可能有波动|系统状态、缓存、调度都会影响时间|
|多次运行更稳定|可以看平均性能|
|方便比较线程数变化|观察 scaling trend|
|减少偶然误差|避免只看一次运行结果|

---

## 15. Worksharing Loop 中应该观察什么？

可以尝试不同线程数：

```bash
export OMP_NUM_THREADS=1
./daxpy

export OMP_NUM_THREADS=2
./daxpy

export OMP_NUM_THREADS=4
./daxpy

export OMP_NUM_THREADS=8
./daxpy
```

观察内容：

|观察项|含义|
|---|---|
|runtime 是否下降|并行是否带来加速|
|speedup 是否接近线程数|并行效率是否高|
|线程数增加后是否变慢|是否出现 overhead 或 memory bandwidth limit|
|不同运行间结果是否稳定|性能是否受系统噪声影响|

## 18. Wall-clock Time 是什么？

课本提到 timer 返回的是 wall-clock time。

`wall-clock time` 指真实世界中经过的时间，也就是你用钟表看到的时间。

例如：

```text
程序从 10:00:00 开始
程序到 10:00:05 结束
wall-clock time = 5 seconds
```

它和 CPU time 不完全一样。

|时间类型|含义|
|---|---|
|Wall-clock time|实际经过时间|
|CPU time|CPU 实际花在计算上的时间|
|Parallel runtime|通常更关心 wall-clock time|

在并行程序中，我们通常关心 wall-clock time，因为目标是让实际等待时间变短。

# Exercise 4: Serial vs OpenMP

## 19. 串行版本 work_serial

课本接着让我们查看：

```text
work_serial.c
work_serial.f90
```

这些版本不再使用：

```text
omp.h
omp_lib
```

并且用具体数值替代 OpenMP 函数调用。

因为代码没有用 OpenMP 编译，所以 OpenMP directives 会被忽略。

---

## 20. 编译和运行串行版本

```bash
make work_serial
./work_serial
```

然后对比 OpenMP 单线程版本：

```bash
export OMP_NUM_THREADS=1
./work
```

预期结果：

> `work_serial` 的速度应该和 `work` 使用 1 个线程时差不多。

---

## 21. 为什么单线程 OpenMP 可能仍然有开销？

即使只使用一个线程，OpenMP 程序也可能有额外开销。

原因包括：

|开销来源|说明|
|---|---|
|parallel region setup|创建或管理线程队伍|
|runtime bookkeeping|OpenMP runtime 需要维护线程信息|
|synchronization|可能存在 barrier 等同步|
|function call overhead|调用 OpenMP 相关函数|
|scheduling overhead|分配工作给线程也有成本|

课本特别指出，因为这个计算时间相对较短，所以 OpenMP overhead 可能比较明显。

一句话：

> OpenMP 不一定在所有情况下都更快，尤其是任务太小时，管理线程的成本可能抵消收益。

# Exercise 5: Hand-coding vs Performance Library

## 22. 练习目标

最后一个练习比较：

1. 手写 OpenMP DAXPY。
    
2. 高性能数学库中的 DAXPY。
    

相关文件：

```text
daxpy2.c
daxpy2.f90
```

DAXPY 是标准 BLAS routine，很多高性能库都实现了它。

例如：

|Library|系统|
|---|---|
|Intel MKL|Frontera|
|NVIDIA NVPL|Vista|

---

## 23. BLAS 是什么？

`BLAS` 全称是：

```text
Basic Linear Algebra Subprograms
```

它是一组标准线性代数接口，包括：

|Routine|功能|
|---|---|
|DAXPY|`y = a*x + y`|
|DGEMV|矩阵-向量乘法|
|DGEMM|矩阵-矩阵乘法|

很多 HPC 程序不会手写底层线性代数操作，而是调用 MKL、OpenBLAS、BLIS、NVPL 等高性能库。

原因：

> 高性能库通常经过深度优化，能更好利用 cache、SIMD、threading 和硬件特性。

---

## 24. 编译和运行 daxpy2

```bash
make daxpy2
export OMP_NUM_THREADS=3
./daxpy2
```

或者：

```bash
make run_daxpy2
```

---

## 25. MKL / NVPL 与 OpenMP 的关系

课本提到，MKL 和 NVPL 中很多 routine 已经用 OpenMP 并行化了。

也就是说，你不一定需要自己写：

```c
#pragma omp parallel for
```

有时候只需要设置：

```bash
export OMP_NUM_THREADS=8
```

然后调用库函数，库内部就会使用多线程。

重要理解：

> 高性能库经常已经内置并行化，盲目在外层再套 OpenMP 可能导致 oversubscription 或性能下降。

---

## 26. DAXPY 的特殊点

课本指出，DAXPY 操作非常简单，因此：

|Library|是否并行化 DAXPY|
|---|---|
|Intel MKL|是|
|NVIDIA NVPL|否|

原因可能是：

> DAXPY 是 memory bandwidth-bound 操作，计算量很少，多线程并行不一定总是值得。

DAXPY 每个元素只做：

```text
one multiply + one add
```

但需要读写多个数组元素，因此瓶颈往往不是 CPU 计算能力，而是内存带宽。

## 28. 如何分析性能图？

比较手写 OpenMP 和 MKL DAXPY 时，可以看：

|指标|问题|
|---|---|
|runtime|哪个版本更快？|
|speedup|线程数增加后是否加速？|
|scaling|加速是否接近线性？|
|saturation point|到几个线程后不再变快？|
|slowdown|线程太多是否反而变慢？|

可以使用这样的分析句式：

```text
As the number of OpenMP threads increases, the runtime initially decreases, indicating useful parallel speedup. However, beyond a certain number of threads, the performance improvement becomes limited, suggesting that the computation may be constrained by memory bandwidth or OpenMP overhead.
```

中文理解：

> 随着线程数增加，运行时间一开始下降，说明并行有效；但超过某个线程数后收益变小，说明可能遇到了内存带宽瓶颈或 OpenMP 开销。

---

## 29. 线程数可以超过物理核心数吗？

课本最后提到：

> The number of OpenMP threads is allowed to exceed the number of physical cores.

也就是说，OpenMP 允许线程数超过物理核心数。

例如机器只有 16 个物理核心，但你可以设置：

```bash
export OMP_NUM_THREADS=32
```

但是这不一定带来性能提升。

|情况|可能结果|
|---|---|
|线程数小于或等于核心数|通常更合理|
|线程数略多于核心数|有时可以隐藏等待开销|
|线程数远超核心数|通常会增加调度和上下文切换开销|
|memory-bound 程序|线程过多可能更快达到带宽上限|

一句话：

> OpenMP 允许 oversubscription，但不代表 oversubscription 会更快。

## 31. 常见易错点

### 31.1 忘记设置 OMP_NUM_THREADS

如果没有设置：

```bash
export OMP_NUM_THREADS=...
```

程序可能使用默认线程数，导致结果和预期不一致。

---

### 31.2 在 login node 上做正式性能测试

login node 适合编辑、编译和小测试，不适合正式 benchmark。

性能测试最好在 dedicated compute node 上进行。

---

### 31.3 以为线程越多一定越快

线程数增加可能带来：

- 更高并行度
    
- 更高同步开销
    
- 更大调度成本
    
- 更强内存带宽竞争
    
- 更严重 cache contention
    

所以线程越多不一定越快。

---

### 31.4 忽略 OpenMP overhead

对于很短的计算任务，OpenMP 管理线程和同步的成本可能比较明显。

如果任务太小：

```text
parallel overhead > computation saved
```

那么并行版本可能不比串行版本快。

---

### 31.5 忽略高性能库已经并行化

调用 MKL 或 NVPL 等库时，要注意库内部可能已经用了 OpenMP。

如果外层再手动开很多 OpenMP 线程，可能导致线程过多，反而降低性能。
