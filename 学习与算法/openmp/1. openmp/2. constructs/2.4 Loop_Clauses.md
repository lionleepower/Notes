# OpenMP Loop Clauses

## 1. 本节核心总结

OpenMP 的 **loop clauses** 是写在 `#pragma omp for` 或 `#pragma omp parallel for` 后面的修饰项，用来控制循环并行化的细节。  
其中最重要的是 `schedule`、`collapse`、`nowait`、`lastprivate` 和 `reduction`。  
`schedule` 决定 loop iterations 如何分配给 threads；`collapse(n)` 可以把多层嵌套循环压平成一个大循环；`nowait` 可以去掉 loop 结尾默认的 barrier；`lastprivate` 可以保留串行语义下最后一次 iteration 的变量值。  
学习这一节时，核心问题是：**不同线程如何分配循环任务，以及什么时候需要同步**。

---

## 2. Loop Clauses 快速总览表

| Clause | 作用 | 常见程度 | 一句话理解 |
|---|---|---|---|
| `private(list)` | 每个线程拥有变量的私有副本 | 高 | loop 内每个线程各用各的变量 |
| `firstprivate(list)` | 私有副本，并从外部复制初始值 | 中 | private + 初始值 |
| `lastprivate(list)` | 私有副本，最后一次 iteration 的值复制回外部 | 中 | 保留串行最后一次循环的结果 |
| `reduction(op:list)` | 各线程局部计算，最后合并 | 高 | 求和、最大值、最小值常用 |
| `ordered` | 标记 loop 内会使用 ordered construct | 低 | 只让特定部分按顺序执行 |
| `schedule(kind[, chunk_size])` | 控制 iterations 如何分配给 threads | 高 | 决定负载均衡和调度开销 |
| `collapse(n)` | 把 n 层嵌套 loop 合并成一个大 loop | 高 | 增加可分配的 iteration 数量 |
| `nowait` | 去掉 loop 结尾的隐式 barrier | 中 | 做完当前 loop 的线程不用等其他线程 |

---

## 3. Loop Clause 的位置

Loop clauses 写在 OpenMP loop directive 后面。

### 写法 1：在 parallel region 内使用 `omp for`

```c
#pragma omp parallel
{
    #pragma omp for schedule(static) reduction(+:sum)
    for (int i = 0; i < n; i++) {
        sum += a[i];
    }
}
````

### 写法 2：使用 combined construct

```c
#pragma omp parallel for schedule(static) reduction(+:sum)
for (int i = 0; i < n; i++) {
    sum += a[i];
}
```

实际中最常见的是第二种：

```c
#pragma omp parallel for [clauses]
for (...) {
    ...
}
```

---

# 4. `private`、`firstprivate` 和 `reduction`

## 4.1 它们在 loop construct 中的含义

`private`、`firstprivate` 和 `reduction` 在 loop construct 中的行为和在 parallel region 中类似。

区别是：

> 在 loop construct 中，这些 clauses 的作用范围是它们修饰的 loop，而不一定是整个 parallel region。

例如：

```c
#pragma omp parallel
{
    #pragma omp for private(x)
    for (int i = 0; i < n; i++) {
        x = i;
    }

    #pragma omp for firstprivate(x)
    for (int i = 0; i < n; i++) {
        // x 的处理方式可能和上一个 loop 不同
    }
}
```

也就是说，如果一个 parallel region 里面有多个连续的 `omp for`，同一个变量在不同 loop 中可以有不同的 sharing attribute。

---

## 4.2 `private`

```c
#pragma omp parallel for private(temp)
for (int i = 0; i < n; i++) {
    temp = b[i] + c[i];
    a[i] = temp;
}
```

含义：

```text
每个线程都有自己的 temp
不同线程之间不会互相覆盖 temp
```

适合临时变量。

---

## 4.3 `firstprivate`

```c
int offset = 10;

#pragma omp parallel for firstprivate(offset)
for (int i = 0; i < n; i++) {
    a[i] = i + offset;
}
```

含义：

```text
每个线程都有自己的 offset
每个 offset 初始值都是进入 loop 前的 10
```

---

## 4.4 `reduction`

```c
double sum = 0.0;

#pragma omp parallel for reduction(+:sum)
for (int i = 0; i < n; i++) {
    sum += a[i];
}
```

含义：

```text
每个线程先计算自己的 local sum
loop 结束后再合并成最终 sum
```

这是并行求和的标准写法。

---

# 5. `lastprivate`

## 5.1 作用

`lastprivate` 和 `private` 类似，都会让变量在每个线程中拥有私有副本。

但它额外做一件事：

> loop 结束后，把“串行执行时最后一次 iteration”对应的变量值复制回外部变量。

语法：

```c
#pragma omp parallel for lastprivate(x)
for (int i = 0; i < n; i++) {
    x = i;
}
```

这里 loop 结束后，`x` 会得到串行语义下最后一次 iteration 的值。

如果 `i` 从 `0` 到 `n - 1`，那么最后一次 iteration 是：

```text
i = n - 1
```

所以最后 `x` 的值应该来自 `i = n - 1` 那次循环。

---

## 5.2 为什么需要 lastprivate？

串行代码中：

```c
int x;

for (int i = 0; i < n; i++) {
    x = i * 2;
}

printf("%d\n", x);
```

loop 结束后，`x` 的值来自最后一次循环。

如果改成 OpenMP：

```c
int x;

#pragma omp parallel for private(x)
for (int i = 0; i < n; i++) {
    x = i * 2;
}

printf("%d\n", x);
```

这里外部 `x` 的值不能可靠使用。

如果确实需要保留最后一次 iteration 的值，应使用：

```c
int x;

#pragma omp parallel for lastprivate(x)
for (int i = 0; i < n; i++) {
    x = i * 2;
}

printf("%d\n", x);
```

当 `n = 10` 时，串行最后一次 iteration 是 `i = 9`，所以最后：

```text
x = 18
```

---

## 5.3 lastprivate 的关键细节

课本中特别强调：

> last iteration 指的是串行执行时最后会执行的那一次 iteration。

这不一定是实际并行执行中最后完成的 iteration。

例如：

```c
#pragma omp parallel for schedule(dynamic) lastprivate(x)
for (int i = 0; i < n; i++) {
    x = i;
}
```

即使 `i = n - 1` 这次 iteration 比其他 iteration 更早完成，最终 `x` 仍然应该来自 `i = n - 1`。

所以：

```text
lastprivate 的 last 指的是 serial order 的 last，不是 wall-clock time 上最后完成的 thread。
```

---

## 5.4 lastprivate 什么时候才有效？

`lastprivate` 的值只有在整个 OpenMP loop 完成后才有效。

也就是说：

```text
所有 iterations 都完成之后
lastprivate 变量才会被复制回 enclosing context
```

如果 loop 还没结束，就不能依赖这个变量的最终值。

---

# 6. `ordered`

## 6.1 作用

`ordered` clause 表示：

> 这个 OpenMP loop 内部会出现 ordered construct。

它只是一个标记，告诉 OpenMP：loop body 里面有部分代码需要按照串行 iteration 顺序执行。

语法大致是：

```c
#pragma omp parallel for ordered
for (int i = 0; i < n; i++) {
    // parallel work

    #pragma omp ordered
    {
        // ordered work
    }
}
```

---

## 6.2 ordered 不代表整个 loop 顺序执行

这是一个很重要的误区。

`ordered` 不表示整个 loop 都按顺序执行。

如果整个 loop 都顺序执行，那就没有并行收益了。

正确理解：

```text
loop 的大部分工作仍然可以并行
只有被 #pragma omp ordered 包住的部分按 iteration 顺序执行
```

---

## 6.3 示例

```c
#pragma omp parallel for ordered
for (int i = 0; i < n; i++) {
    double result = expensive_work(i);

    #pragma omp ordered
    {
        printf("i = %d, result = %f\n", i, result);
    }
}
```

这里：

- `expensive_work(i)` 可以并行执行
    
- `printf` 部分按照 `i = 0, 1, 2, ...` 的顺序输出
    

---

## 6.4 初学阶段如何看 ordered？

你可以先记住：

```text
ordered 用得不多，主要用于 loop 中只有一小部分代码必须保持串行顺序的情况。
```

如果大部分 loop body 都需要 ordered，那么这个 loop 通常不适合 OpenMP 并行。

---

# 7. `schedule`

## 7.1 schedule 的作用

`schedule` clause 决定：

> loop iterations 如何分配给 threads。

语法：

```c
#pragma omp parallel for schedule(kind[, chunk_size])
for (int i = 0; i < n; i++) {
    ...
}
```

其中：

- `kind` 表示调度方式
    
- `chunk_size` 表示每次分配多少个连续 iterations
    

例如：

```c
#pragma omp parallel for schedule(static, 4)
for (int i = 0; i < n; i++) {
    ...
}
```

含义是：

```text
以 4 个 iterations 为一个 chunk
按照 static 策略分配给不同 threads
```

---

## 7.2 四种 schedule kind 总览

|Schedule kind|分配方式|适合场景|缺点|
|---|---|---|---|
|`static`|开始前固定分配|每次 iteration 工作量相近|负载不均时可能慢|
|`dynamic`|线程空闲后再领取新 chunk|iteration 工作量不均|调度开销更高|
|`guided`|类似 dynamic，但 chunk 从大到小|不均衡任务，想减少 dynamic overhead|行为较复杂|
|`runtime`|运行时由 `OMP_SCHEDULE` 决定|不重新编译即可调参|依赖环境变量|

---

# 8. `schedule(static)`

## 8.1 作用

`static` scheduling 表示：

> loop iterations 在执行开始时就固定分配给各个 threads。

如果指定了 `chunk_size`，则按 chunk size 分块，并按照线程编号 round-robin 分配。

例如：

```c
#pragma omp parallel for schedule(static, 2)
for (int i = 0; i < 8; i++) {
    work(i);
}
```

假设有 2 个 threads，那么可能分配为：

```text
Thread 0: i = 0,1 和 i = 4,5
Thread 1: i = 2,3 和 i = 6,7
```

因为 chunk size 是 2，所以 chunks 是：

```text
Chunk 0: 0,1
Chunk 1: 2,3
Chunk 2: 4,5
Chunk 3: 6,7
```

然后 round-robin 分配给线程。

---

## 8.2 不指定 chunk size 的 static

```c
#pragma omp parallel for schedule(static)
for (int i = 0; i < 8; i++) {
    work(i);
}
```

如果有 4 个 threads，通常会近似平均分配：

```text
Thread 0: i = 0,1
Thread 1: i = 2,3
Thread 2: i = 4,5
Thread 3: i = 6,7
```

---

## 8.3 static 适合什么场景？

`static` 适合：

```text
每个 iteration 的工作量差不多
```

例如：

```c
#pragma omp parallel for schedule(static)
for (int i = 0; i < n; i++) {
    a[i] = b[i] + c[i];
}
```

这里每次循环做的事情几乎一样，所以 static 通常很好。

优点：

- 调度开销低
    
- 数据访问模式稳定
    
- 对 cache locality 可能更友好
    
- 结果更容易复现和分析
    

缺点：

- 如果某些 iterations 明显更慢，可能导致 load imbalance
    

---

# 9. `schedule(dynamic)`

## 9.1 作用

`dynamic` scheduling 表示：

> threads 不是一开始拿到固定任务，而是谁先空闲，谁就再领取新的 chunk。

语法：

```c
#pragma omp parallel for schedule(dynamic, chunk_size)
```

如果不写 `chunk_size`，默认通常是 1。

---

## 9.2 示例

```c
#pragma omp parallel for schedule(dynamic, 1)
for (int i = 0; i < n; i++) {
    work_with_variable_cost(i);
}
```

假设某些 `i` 很慢，某些 `i` 很快。

`dynamic` 的好处是：

```text
快的线程做完后可以继续拿新任务
慢的线程不会让其他线程一直闲着
```

---

## 9.3 dynamic 适合什么场景？

`dynamic` 适合：

```text
不同 iterations 的工作量差异很大
```

例如：

```c
#pragma omp parallel for schedule(dynamic)
for (int i = 0; i < n; i++) {
    if (is_hard_case(i)) {
        expensive_work(i);
    } else {
        cheap_work(i);
    }
}
```

优点：

- 更容易解决 load imbalance
    
- 线程利用率可能更高
    

缺点：

- 调度开销比 static 更高
    
- 默认 chunk size 为 1 时，overhead 可能明显
    
- 数据 locality 可能变差
    

---

# 10. `schedule(guided)`

## 10.1 作用

`guided` scheduling 类似 dynamic：

```text
线程空闲后继续领取新的 iterations
```

但它的 chunk size 不是固定的，而是：

```text
一开始 chunk 比较大
后面 chunk 逐渐变小
```

这意味着：

- 前期大块分配，减少调度开销
    
- 后期小块分配，改善负载均衡
    

---

## 10.2 guided 的直觉

可以这样理解：

```text
dynamic:
每次都发小任务，负载均衡好，但 overhead 高

guided:
一开始发大任务，overhead 低
快结束时发小任务，让大家尽量同时结束
```

---

## 10.3 guided 适合什么场景？

`guided` 适合：

```text
iteration 工作量不均，但又不想承受 dynamic 的过高调度开销
```

例如：

```c
#pragma omp parallel for schedule(guided)
for (int i = 0; i < n; i++) {
    variable_cost_work(i);
}
```

如果指定 chunk size：

```c
#pragma omp parallel for schedule(guided, 4)
```

这里的 `4` 通常表示后期 chunk size 的下界，不会继续小到低于这个值。

---

# 11. `schedule(runtime)`

## 11.1 作用

`runtime` scheduling 表示：

> schedule 的 kind 和 chunk size 不在代码里写死，而是由环境变量 `OMP_SCHEDULE` 控制。

代码：

```c
#pragma omp parallel for schedule(runtime)
for (int i = 0; i < n; i++) {
    work(i);
}
```

运行时设置：

```bash
export OMP_SCHEDULE="static"
```

或者：

```bash
export OMP_SCHEDULE="dynamic,4"
```

这样可以不重新编译程序，直接测试不同 schedule 的性能。

---

## 11.2 runtime 适合什么场景？

适合性能调参：

```text
同一份代码
多次运行
比较 static / dynamic / guided / chunk size 的性能
```

例如在 HPC benchmark 中很有用。

---

# 12. schedule 如何选择？

## 12.1 简单选择原则

|情况|推荐 schedule|
|---|---|
|每次 iteration 工作量差不多|`schedule(static)`|
|工作量不均，但每个 iteration 较大|`schedule(dynamic, chunk)`|
|工作量不均，又想减少调度开销|`schedule(guided)`|
|想实验不同策略，不想重新编译|`schedule(runtime)`|
|不确定时|先试 `static`，再 benchmark|

---

## 12.2 chunk size 怎么理解？

`chunk_size` 表示：

```text
一次分配给某个 thread 的连续 iterations 数量
```

例如：

```c
#pragma omp parallel for schedule(dynamic, 8)
```

意思是：

```text
每次空闲线程领取 8 个连续 iterations
```

chunk size 的影响：

|chunk size|优点|缺点|
|---|---|---|
|小|负载均衡更好|调度开销更大|
|大|调度开销更小，locality 可能更好|负载不均风险更高|

简单记忆：

```text
小 chunk 更均衡，大 chunk 更省调度开销。
```

---

# 13. `collapse(n)`

## 13.1 作用

`collapse(n)` 用于把嵌套循环的前 `n` 层合并成一个更大的 iteration space，然后再并行分配。

语法：

```c
#pragma omp parallel for collapse(2)
for (int i = 0; i < n; i++) {
    for (int j = 0; j < m; j++) {
        work(i, j);
    }
}
```

原本外层只有 `n` 个 iterations。  
使用 `collapse(2)` 后，OpenMP 看到的是：

```text
n × m 个 combined iterations
```

---

## 13.2 为什么需要 collapse？

如果外层循环次数很少，但线程很多，普通并行可能无法充分利用线程。

例如：

```c
#pragma omp parallel for
for (int i = 0; i < 4; i++) {
    for (int j = 0; j < 1000; j++) {
        work(i, j);
    }
}
```

如果有 16 个 threads，但外层只有 4 个 iterations，那么最多只能有效分给 4 个线程。

使用：

```c
#pragma omp parallel for collapse(2)
for (int i = 0; i < 4; i++) {
    for (int j = 0; j < 1000; j++) {
        work(i, j);
    }
}
```

OpenMP 会把总 iteration space 视为：

```text
4 × 1000 = 4000 iterations
```

这样更容易分配给 16 个 threads。

---

## 13.3 collapse 示例

```c
#pragma omp parallel for collapse(2) private(j)
for (int i = 0; i < 10; i++) {
    for (int j = 0; j < 100; j++) {
        a[i][j] = b[i][j] + c[i][j];
    }
}
```

这里 `collapse(2)` 表示把 `i` 和 `j` 两层循环合并后再调度。

---

## 13.4 collapse 的限制

被 collapse 的 loops 必须满足：

```text
iterations 之间不能有依赖
loop 结构最好是 rectangular loops
iteration variables 之间不能互相依赖
```

所谓 rectangular loop，就是每一层循环的范围规则稳定，例如：

```c
for (int i = 0; i < n; i++) {
    for (int j = 0; j < m; j++) {
        ...
    }
}
```

这是规则矩形结构。

不适合 collapse 的例子：

```c
#pragma omp parallel for collapse(2)
for (int i = 0; i < n; i++) {
    for (int j = 0; j < i; j++) {
        work(i, j);
    }
}
```

这里内层 `j` 的范围依赖 `i`，不是典型 rectangular loop。  
这种情况下使用 `collapse` 要非常小心。

---

## 13.5 collapse 和 schedule 的关系

`collapse(n)` 会增加需要调度的 iteration 数量。

因此课本建议：

```text
collapse 通常可以先搭配 static scheduling 作为默认尝试。
```

例如：

```c
#pragma omp parallel for collapse(2) schedule(static)
for (int i = 0; i < n; i++) {
    for (int j = 0; j < m; j++) {
        a[i][j] = b[i][j] + c[i][j];
    }
}
```

# 14. `nowait`

## 14.1 OpenMP loop 结尾默认有 barrier

在 OpenMP 中，每个 loop construct 末尾默认有一个隐式 barrier。

也就是说：

```c
#pragma omp parallel
{
    #pragma omp for
    for (int i = 0; i < n; i++) {
        work1(i);
    }

    // 所有线程必须等在这里
    // 等第一个 loop 的所有 iterations 都完成后，才能继续往下执行

    #pragma omp for
    for (int i = 0; i < n; i++) {
        work2(i);
    }
}
```

默认情况下：

```text
所有线程完成第一个 loop
同步等待
然后所有线程再进入第二个 loop
```

---

## 14.2 nowait 的作用

`nowait` 用来去掉 loop 结尾的隐式 barrier。

语法：

```c
#pragma omp for nowait
for (int i = 0; i < n; i++) {
    work1(i);
}
```

含义：

```text
某个线程完成自己在这个 loop 中的任务后
不用等待其他线程
可以继续执行后面的代码
```

---

## 14.3 nowait 适合什么场景？

`nowait` 最适合多个相互独立的 loops 在同一个 parallel region 中连续出现时使用。

例如：

```c
#pragma omp parallel
{
    #pragma omp for nowait
    for (int i = 0; i < n; i++) {
        a[i] = b[i] + c[i];
    }

    #pragma omp for
    for (int i = 0; i < n; i++) {
        x[i] = y[i] * z[i];
    }
}
```

如果两个 loop 之间没有数据依赖，那么第一个 loop 后面不一定需要 barrier。

---

## 14.4 nowait 不能乱用

如果第二个 loop 依赖第一个 loop 的结果，就不能随便加 `nowait`。

错误例子：

```c
#pragma omp parallel
{
    #pragma omp for nowait
    for (int i = 0; i < n; i++) {
        a[i] = b[i] + c[i];
    }

    #pragma omp for
    for (int i = 0; i < n; i++) {
        d[i] = a[i] * 2.0;
    }
}
```

这里第二个 loop 使用了第一个 loop 计算出来的 `a[i]`。

如果加了 `nowait`，可能某些线程已经开始读取 `a[i]`，但另一些线程还没完成写入，导致错误或不稳定结果。

正确写法是保留默认 barrier：

```c
#pragma omp parallel
{
    #pragma omp for
    for (int i = 0; i < n; i++) {
        a[i] = b[i] + c[i];
    }

    #pragma omp for
    for (int i = 0; i < n; i++) {
        d[i] = a[i] * 2.0;
    }
}
```

---

## 14.5 nowait 与 lastprivate / reduction

课本中特别提到：

> lastprivate or reduction variables from a loop construct do not become valid until a barrier has been encountered after their loop is complete.

意思是：

如果一个 loop 使用了 `lastprivate` 或 `reduction`，它们的最终结果要到 barrier 之后才可靠。

因此：

```text
如果使用 nowait 去掉了 loop 末尾 barrier
那么不要立刻依赖该 loop 的 lastprivate 或 reduction 最终值
除非后面又遇到了一个 barrier
```

例如不推荐：

```c
#pragma omp parallel
{
    double sum = 0.0;

    #pragma omp for reduction(+:sum) nowait
    for (int i = 0; i < n; i++) {
        sum += a[i];
    }

    // 此处不应立即依赖 sum 的最终 reduction 结果
}
```

# 15. 综合例子

## 15.1 使用 schedule 和 reduction

```c
double sum = 0.0;

#pragma omp parallel for schedule(static) reduction(+:sum)
for (int i = 0; i < n; i++) {
    sum += a[i];
}
```

解释：

```text
schedule(static): iterations 固定分配，适合工作量均匀的循环
reduction(+:sum): 每个线程局部求和，最后合并
```

---

## 15.2 使用 collapse 并行二维循环

```c
#pragma omp parallel for collapse(2) schedule(static)
for (int i = 0; i < n; i++) {
    for (int j = 0; j < m; j++) {
        a[i][j] = b[i][j] + c[i][j];
    }
}
```

解释：

```text
collapse(2): 合并 i 和 j 两层循环
schedule(static): 把合并后的 iteration space 静态分配给 threads
```

适合：

```text
二维数组每个元素独立更新
外层循环数量较少
希望增加并行粒度
```

---

## 15.3 使用 nowait 优化独立 loops

```c
#pragma omp parallel
{
    #pragma omp for nowait
    for (int i = 0; i < n; i++) {
        a[i] = b[i] + c[i];
    }

    #pragma omp for nowait
    for (int i = 0; i < n; i++) {
        x[i] = y[i] * z[i];
    }

    #pragma omp for
    for (int i = 0; i < n; i++) {
        p[i] = q[i] - r[i];
    }
}
```

解释：

```text
三个 loops 之间相互独立
前两个 loop 后不强制 barrier
最后一个 loop 结尾保留默认 barrier
```

# 16. 常见错误总结

## 16.1 错误 1：以为 `ordered` 会让整个 loop 串行执行

错误理解：

```text
#pragma omp parallel for ordered
表示整个 loop 按顺序执行
```

正确理解：

```text
ordered 只是允许 loop 内部使用 #pragma omp ordered
只有 ordered block 内的代码按顺序执行
```

---

## 16.2 错误 2：所有情况都用 dynamic

`dynamic` 不一定比 `static` 快。

如果每次 iteration 工作量差不多：

```c
#pragma omp parallel for schedule(dynamic)
for (int i = 0; i < n; i++) {
    a[i] = b[i] + c[i];
}
```

可能比 `static` 更慢，因为 dynamic 有额外调度开销。

更适合：

```c
#pragma omp parallel for schedule(static)
for (int i = 0; i < n; i++) {
    a[i] = b[i] + c[i];
}
```

---

## 16.3 错误 3：使用 nowait 但后面有数据依赖

错误：

```c
#pragma omp parallel
{
    #pragma omp for nowait
    for (int i = 0; i < n; i++) {
        a[i] = f(i);
    }

    #pragma omp for
    for (int i = 0; i < n; i++) {
        b[i] = a[i] + 1;
    }
}
```

问题：

```text
第二个 loop 依赖第一个 loop 的结果
不能去掉第一个 loop 后面的 barrier
```

---

## 16.4 错误 4：collapse 用在有依赖的 nested loops 上

错误：

```c
#pragma omp parallel for collapse(2)
for (int i = 1; i < n; i++) {
    for (int j = 1; j < m; j++) {
        a[i][j] = a[i-1][j] + a[i][j-1];
    }
}
```

问题：

```text
每个 iteration 依赖相邻元素
iterations 之间不独立
不能简单 collapse 并行化
```

---

## 16.5 错误 5：以为 lastprivate 是“最后完成的线程”的值

错误理解：

```text
lastprivate 保存最后完成的那个 thread 的值
```

正确理解：

```text
lastprivate 保存串行语义下最后一次 iteration 的值
```

# 17. 如何选择 Loop Clauses？

## 17.1 基础选择流程

```text
1. 这个 loop 能不能并行？
   - iterations 是否独立？
   - 是否有 loop-carried dependency？

2. 是否有共享变量更新？
   - 求和、最大值、最小值：用 reduction
   - 临时变量：用 private

3. iteration 工作量是否均匀？
   - 均匀：schedule(static)
   - 不均匀：schedule(dynamic) 或 schedule(guided)

4. nested loop 外层 iteration 是否太少？
   - 是：考虑 collapse(n)

5. loop 后是否需要等待所有线程？
   - 有数据依赖：保留默认 barrier
   - 无数据依赖：可以考虑 nowait
```

---

# 18. 本节重点

- Loop clauses 用来控制 OpenMP loop 的变量作用域、调度方式和同步行为。
    
- `private`、`firstprivate`、`reduction` 在 loop 中作用范围是对应 loop。
    
- `lastprivate` 保存串行语义下最后一次 iteration 的变量值。
    
- `ordered` 只表示 loop 内会有 ordered block，不代表整个 loop 顺序执行。
    
- `schedule(static)` 适合工作量均匀的循环。
    
- `schedule(dynamic)` 适合 iteration 工作量不均的循环，但有更多调度开销。
    
- `schedule(guided)` 是 dynamic 的折中版本，前期大 chunk，后期小 chunk。
    
- `schedule(runtime)` 允许通过 `OMP_SCHEDULE` 在运行时选择调度策略。
    
- `collapse(n)` 可以把多层 nested loops 合并成更大的 iteration space。
    
- `nowait` 可以去掉 loop 末尾默认 barrier，但只能在没有依赖时使用。
    
- 使用 `nowait` 后，不能立即依赖该 loop 的 `lastprivate` 或 `reduction` 结果，除非后面遇到 barrier。

# 19. 一句话记忆

```text
schedule 决定 iterations 怎么分，collapse 决定 nested loops 怎么合并，nowait 决定 loop 结束后要不要等，lastprivate 决定是否保留串行最后一次 iteration 的值。
```

```text
static 省开销，dynamic 管不均衡，guided 折中，runtime 方便调参。
```
