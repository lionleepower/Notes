## 1. 源代码层面的发现：`--with-openmp-kernels` 实际覆盖了什么

PETSc 通过两个宏提供 OpenMP 内核线程化功能（位于 `include/petscmacros.h`）：

- `PetscPragmaOMP(...)`：启用 `--with-openmp` 时生效。
- `PetscPragmaUseOMPKernels(...)`：启用 `--with-openmp-kernels` 时生效。

**对 `src/` 和 `include/` 进行 grep 并验证后，得到内核线程化位置的完整列表：**

|宏的位置|函数|文件与行号|
|---|---|---|
|`PetscPragmaUseOMPKernels(parallel for)`|`MatMult_SeqAIJ`（两个分支）|`src/mat/impls/aij/seq/aij.c:1495, 1509`|
|`PetscPragmaUseOMPKernels(parallel for)`|`MatMultAdd_SeqAIJ`|`src/mat/impls/aij/seq/aij.c:1665`|
|`PetscPragmaUseOMPKernels(parallel for ... reduction)`|`MatMult_SeqAIJ_Inode`|`src/mat/impls/aij/seq/inode.c:371`|
|`PetscPragmaUseOMPKernels(parallel for)` ×4|`PetscKernelAXPY` 模板|`include/petsc/private/kernels/petscaxpy.h:203, 214, 227, 242`|

**关键结论：**PETSc 的内核级线程化仅限于 **MatMult（SpMV）系列**。单独启用 `--with-openmp` 不会引入任何多线程数值循环。它仅用于两个 `omp critical` 保护区，以确保浮点异常捕获的线程安全（`src/sys/error/fp.c:62, 89`）；此外，它还通过 `PetscPragmaSIMD` 间接启用 `omp simd`，但这属于向量化而非多线程，并且在 `vec/impls/seq` 中没有使用。

### 求解路径中的线程化缺口

GAMG 使用的 Chebyshev 平滑器在每次迭代中会调用三个向量内核。这些内核都是手写的 C 循环，且没有使用线程化宏：

|内核|实现|文件与行号|本测试中每次求解的调用次数|
|---|---|---|---|
|`VecAYPX_Seq`|`y = x + a*y` 循环|`src/vec/vec/impls/seq/dvec2.c:753`|405|
|`VecAXPBYPCZ_Seq`|`z = a*x + b*y + c*z` 循环|`src/vec/vec/impls/seq/bvec1.c:120`|132|
|`VecPointwiseMult_Seq`|`w = x*y` 循环|`src/vec/vec/impls/seq/bvec2.c:72`|330|

MPI 并行向量会把每个进程内的工作**直接分派给这些 `_Seq` 实现**（`src/vec/vec/impls/mpi/pbvec.c:468–471`），因为逐点向量运算不需要通信。因此，只需对 `_Seq` 实现进行线程化，一处修改就能同时覆盖串行向量和分布式向量。

调用次数的来源如下：Chebyshev 平滑器（`src/ksp/ksp/impls/cheby/cheby.c`）调用 `VecAYPX` 更新残差和迭代解，调用 `VecAXPBYPCZ` 实现三项递推；`VecPointwiseMult` 则来自 Jacobi 对角缩放。调用次数随以下因素的乘积变化：

```
GAMG 层数 × 平滑器扫描次数 × CG 迭代次数
```

`VecAXPY`、`VecDot` 和 `VecNorm` 并不是手写循环，而是调用 BLAS（例如 `BLASaxpy_`，见 `bvec1.c:70`）。使用 `--download-fblaslapack` 时，PETSc 使用单线程参考 BLAS，因此无论 OpenMP 如何设置，这些操作都会保持串行。这属于另一类问题——需要多线程 BLAS，而不是增加一个宏——因此不属于本次内核宏工作的范围。

### MatMultTranspose：存在数据竞争，不能简单添加宏

`MatMultTranspose_SeqAIJ`（`aij.c:1457`）只是一个简单的包装函数，执行 `VecSet(0)` 后调用 `MatMultTransposeAdd_SeqAIJ`。

真正的循环位于 `aij.c:1438–1448`，执行列散射写入：

```
y[idx[j]] += alpha * v[j]
```

不同的行 `i` 可能写入同一个 `y[idx[j]]`。因此，若直接按行添加 `parallel for`，就会产生写入竞争。这也解释了为什么上游实现没有将其线程化。

正确的线程化方案需要使用以下方法之一：

- 原子操作；
- 线程私有累加缓冲区及归约；
- 预先转换为 CSC 格式。

其复杂度比三个无数据竞争的 Vec 内核高一个层级，因此被列为拓展目标。

## 2. 基准测试方法修正

### 2.1 单次求解造成的测量偏差

原始 `ex2` 只调用一次 `KSPSolve`。GAMG 的初始化需要构建多重网格层次结构，包括：

- 图粗化；
- 延拓算子平滑；
- Galerkin 矩阵乘积。

这些工作属于一次性成本，因而会主导整个运行时间，使 `KSPSolve` 看起来几乎可以忽略。

实际应用程序，例如时间步进和 Newton 迭代，通常只构建一次预条件器，然后执行**多次**求解，从而摊销初始化成本。因此，单次求解基准测试测量的是对求解阶段最不利的场景，并低估了求解阶段内核优化的重要性。

### 2.2 `ex2_repeat` 驱动程序（`drivers/ex2_repeat.c`）

该程序基于 `src/ksp/ksp/tutorials/ex2.c`，只进行了四项最小修改：

1. 增加 **`-num_solves N`** 选项。默认值为 1，与原始程序行为一致。
2. 在循环外执行一次**预热求解**，由它承担 `PCSetUp` 的成本，并将其保留在默认的 _Main Stage_ 中。
3. 将剩余的 **`N-1` 次计时求解**放入名为 _RepeatedSolves_ 的专用 `PetscLogStage`。这样，`-log_view` 可以在独立表格中报告摊销后的稳态性能，并与初始化阶段清楚分离。
4. 每次求解之前执行 **`VecSet(x, 0.0)`**。如果不这样做，上一次求解得到的解已经满足收敛容差，后续求解会在第 0 次迭代直接退出。验证结果表明，所有重复求解都报告完整的迭代次数，例如 10～11 次。

各次求解之间算子保持不变，因此预条件器会自动复用。命令行中仍显式传入 `-ksp_reuse_preconditioner` 和 `-pc_gamg_reuse_interpolation true`，以明确表达这一意图，同时为以后支持矩阵变化的时间步进版本做好准备。

**效果：**当 `N=20` 时，`KSPSolve` 占总运行时间的比例从 16 节点单次求解测试中的约 1% 上升至 **78～84%**。这提供了一个更具代表性的场景，可用于评估求解阶段的内核线程化。

实验确认 `PCSetUp` 只运行一次（`Count=1`），且每次求解的耗时稳定。例如：

```
64.1 秒 / 19 ≈ 3.4 秒
```

### 2.3 测试框架的健壮性修复（`scripts/ksp/2d/test.sbatch`）

在构建测量框架时发现并修复了多个问题。由于每个问题都可能在没有明显报错的情况下破坏实验结果，因此值得在“可复现性／实验方法”附录中加以说明。

- **MPI 任务数被静默丢失。**  
    使用 `srun --ntasks-per-node=R` 而没有显式指定 `--ntasks` 时，会继承作业环境中的 `SLURM_NTASKS`。如果 `#SBATCH` 头部没有声明任务数，Slurm 会将其设为 1。结果是启动器实际只运行了 **1 个进程而非 16 个**，但日志文件名仍然标记为计划使用的 16 个进程，即文件名所表达的配置与实际运行配置不一致。修复方法是显式指定：
    
    ```
    srun --ntasks=$((R*NODES))
    ```
    
- **环境变量没有正确传递。**  
    使用 `PPN=16 sbatch ...` 依赖 Slurm 的环境变量导出策略。如果变量没有传播，脚本就会回退到默认值，从而运行错误的配置。修复方法是增加：
    
    ```
    #SBATCH --export=ALL
    ```
    
    同时将预期的参数扫描配置写入脚本默认值。
    
- **运行后的自验证。**  
    脚本现在会从 PETSc 日志中解析实际进程数和线程数：
    
    ```
    with N processes
    Using N OpenMP threads
    ```
    
    如果实际配置与预期配置不一致，脚本会立即**终止**，而不是向 CSV 中写入标签错误的数据行。实际进程数和线程数也会记录在 CSV 的 `actual_procs` 和 `actual_threads` 列中。
    
- **解析错误。**  
    迭代次数原本使用 $NF-2 提取。在 awk 中，这表示“最后一个字段的数值减 2”，而不是“倒数第三个字段”。正确写法是 `$(NF-2)`。原写法会在没有报错的情况下写入错误的迭代次数。
    

**可引用的方法论结论：**必须使用独立来源——本例中为 PETSc 自己输出的程序头信息——验证“实际执行的配置”是否等于“预期配置”，因为 HPC 启动器可能会静默替换进程／线程布局。

## 3. 定量实验结果

### 3.1 修正后的 KSPSolve 运行时间占比

重新扫描全部 341 个归档的 `-log_view` 日志（二维和三维弱扩展系列）后，得到 `KSPSolve` 占总运行时间的比例为 **6～31%**，而不是此前假定的 1～11%。此前的数据来自 16 节点固定问题规模系列。

在单节点、128 个 MPI 进程、每进程 1 个线程的配置下：

- 二维：约 **30～31%**
- 三维：约 **15～16%**

随着节点数以及每个进程的线程数增加，该比例会下降。

**引用这一数值时必须明确指出所使用的扩展系列。**单次求解、16 节点测试中的“1%”与单节点测试中的“31%”，实际上是相同代码在不同分解方式下测得的结果。

### 3.2 单进程线程扩展性：干净的对照实验

使用单个 MPI 进程，在 _RepeatedSolves_ 阶段中只改变 `OMP_NUM_THREADS`，从 1 增加到 8。各内核的汇总性能如下：

|内核|是否有宏|t=1|t=8|加速比|
|---|---|---|---|---|
|MatMult|是|1224|3496|**2.9×**|
|MatMultAdd|是|456|3100|**6.8×**|
|MatMultTranspose|否|447|442|1.0×|
|VecAYPX|否|1770|1758|1.0×|
|VecAXPBYPCZ|否|4431|4390|1.0×|
|VecPointwiseMult|否|964|966|1.0×|
|**KSPSolve（实际时间）**|—|114.0 秒|64.1 秒|**1.78×**|

可用于论文撰写的解释如下。

1. **宏是唯一的差异。**  
    `MatMultAdd` 和 `MatMultTranspose` 操作的是**相同的 GAMG 延拓矩阵**，浮点运算次数也完全相同，均为 `7.04e9`。串行情况下，两者速度几乎一致，分别为 456 和 447 MF/s。使用 8 个线程后，两者分别达到 3100 和 442 MF/s。
    
    两者之间唯一的区别就是一行线程化宏。这是最直接的证据，表明线程化确实生效，同时也证明缺少该宏正是另一个内核保持串行的原因。
    
2. **加速比由内存带宽决定，而不是由线程数决定。**  
    `MatMult` 只获得了 2.9× 而不是 8× 的加速，因为单个线程已经使用了相当一部分单核可获得的内存带宽，8 个线程只能进一步使带宽趋于饱和。
    
    `MatMultAdd` 获得了 6.8× 加速，因为它作用于规模较小、可以放入缓存的粗网格矩阵，尚未触及内存带宽上限。
    
    **这也为自行开发的补丁设定了合理预期：**目标 Vec 内核属于纯流式操作，预期加速比应为约 2～3×，而不是 8×。不能承诺线性加速，因为 ARCHER2 上的这些运算受内存带宽限制。这可以作为屋顶线模型分析的材料。
    
3. **Amdahl 定律的时间核算完全吻合。**  
    从 t=1 增加至 t=8 后，求解时间减少了 49.9 秒。其中：
    
    - `MatMult` 节省 37.0 秒；
    - `MatMultAdd` 节省 13.1 秒；
    - 合计节省 50.1 秒。
    
    换言之，**全部性能提升都来自仅有的两个已线程化内核**。
    
    在 t=8 时剩余的 64.1 秒中，未线程化目标约占一半：
    
    ```
    MatMultTranspose：15.9 秒
    VecAYPX：           7.2 秒
    VecAXPBYPCZ：       3.0 秒
    VecPointwiseMult：  5.5 秒
    合计：             31.6 秒
    ```
    
    即稳态求解阶段的 **49%**。
    
4. **正确性基线。**  
    t=1 与 t=8 的误差范数和迭代次数在比特层面完全相同：
    
    ```
    误差范数：0.0124822
    迭代次数：11
    ```
    
    按行并行且不改变归约顺序的线程化不会改变数值结果。这也应成为自行开发补丁的验收标准。
    

### 3.3 NUMA 布局会干扰简单的混合并行对比

在默认 `--distribution=block:block` 配置下，对比以下两种布局：

```
16 个进程 × 1 个线程
16 个进程 × 8 个线程
```

未线程化的 `VecAYPX` 看起来获得了每进程约 **10×** 的性能提升，从 184 Mflop/s 增加到 1872 Mflop/s。

由于该内核既没有使用线程，也没有发送 MPI 消息，这显然不可能是线程化效果。真正原因是 ARCHER2 的节点拓扑：

```
2 × AMD EPYC 7742
每节点 8 个 NUMA 区域
每个 NUMA 区域 16 个核心、2 个内存通道
```

- 对于 16 个进程 × 1 个核心，进程被放置在核心 0～15，即全部位于**一个 NUMA 区域**。16 个进程争用 2 个内存通道，每个进程平均只能获得约 1/8 个通道。
- 对于 16 个进程 × 8 个核心，整个节点被填满，每个 NUMA 区域放置 2 个进程，每个进程平均可获得约 1 个内存通道。

因此，每进程可用内存带宽相差约 8×，与观测到的约 10× 性能差异吻合。

内部一致性也支持这一解释：

- 单独运行的一个进程：`VecAYPX` 为 1770 MF/s；
- 分散放置的 16 个进程：每进程 1872 MF/s；
- 挤在同一 NUMA 区域的 16 个进程：每进程只有 184 MF/s。

论文中应指出两点：

1. 简单比较纯 MPI 与混合并行时，测得的加速部分来自进程在 NUMA 区域中的“分散放置”，而不是 OpenMP 完成了更多工作；必须将两者区分开。
2. 生产级基准测试必须使用**完全填满的节点**，即使用全部 128 个核心，从而消除这种布局偏差。评估补丁前后性能时，两边必须使用相同的固定配置，使布局因素相互抵消。

## 4. 实现范围及依据

- **核心交付目标：**  
    在 `VecAYPX_Seq`、`VecAXPBYPCZ_Seq` 和 `VecPointwiseMult_Seq` 中加入：
    
    ```
    PetscPragmaUseOMPKernels(parallel for)
    ```
    
    其风格与现有 `petscaxpy.h` 保持一致。这些循环不存在数据竞争；修改一个分派位置即可同时覆盖串行向量和 MPI 向量，因此风险较低。
    
- **拓展目标：**  
    使用线程私有缓冲区、原子操作或 CSC 转置方法实现 `MatMultTranspose_SeqAIJ` 的线程化。该内核存在数据竞争，风险更高，但它是最大的单个未线程化项目，在 t=8 时约占稳态求解阶段的 25%。
    
- **应在论文中明确陈述的理由：**  
    从纯 MPI 转向混合并行时，未线程化内核会静默损失约 8× 的并行度。在同样使用 128 个核心的情况下，未线程化循环的并行度从 128 路下降到 16 路。弥补这一覆盖缺口，是公平比较混合并行与纯 MPI 的前提，也能补全 `--with-openmp-kernels` 当前不完整的覆盖范围。
    
- **验收标准：**  
    完成实现、实验评估和结果解释。不承诺一定获得正向加速，因为这些内核受内存带宽限制；同时要求结果在比特层面完全一致。
    

### 预先登记的预测：实现前声明，实现后验证

根据 Amdahl 分解，如果将四个目标内核全部线程化，预计 t=8 的求解阶段时间将从 64.1 秒下降到约：

```
42 ± 5 秒
```

即进一步获得约 **1.5×** 的加速。

这一预测基于以下假设：

- `MatMultTranspose` 的表现与缓存友好的粗网格算子相近；
- Vec 内核可获得约 2～3× 的加速。

无论最终结果是否符合预测，采用“**预测 → 实现 → 解释偏差**”的结构，都能形成最有说服力的评估叙事。
