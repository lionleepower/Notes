
# 「parallel efficiency 大于 100% 合理吗？」——超线性加速物理上什么时候发生（提示：cache）


具体机制，带数字：

- 假设求解器的工作集（矩阵 + 向量，就是每步迭代要反复扫的那堆数组）有 **200 MB**，一个核的可用 cache（L2 + 分到的 L3）只有 **20 MB**。
- 单核跑：200 MB 装不进 20 MB，每一轮迭代扫到的数据大部分早被挤出 cache 了，几乎每次访问都要去 DRAM，慢。
- 分给 16 个核：每核工作集 200/16 = **12.5 MB，小于 20 MB，整份装进 cache**。第一轮迭代之后，数据一直待在 cache 里，后续访问全是 cache hit。
- 结果：每个核不仅活少了 16 倍，**每条数据的处理速度还提升了**（DRAM 延迟 ~100ns vs L2 ~5ns）。16 份 × 每份更快 = 总加速 > 16，E > 100%。


加速比（speedup）通常定义为 `S(p) = T(1) / T(p)`，即单核跑的时间除以 p 个核跑的时间。并行效率（parallel efficiency）是 `E(p) = S(p) / p`,也就是加速比除以核心数。

理想情况下，p 个核最多快 p 倍，所以 `S(p) ≤ p`、`E(p) ≤ 100%`。这是大家的直觉，也是绝大多数情况的现实——因为并行还有通信、同步、负载不均等开销，效率通常是**低于** 100% 的。

所以问题就来了：既然理论上限是 p 倍，怎么可能出现 `S(p) > p`、效率超过 100%？

**核心答案：因为 `T(1)` 这个"基准"本身就跑得偏慢**

超线性加速的本质，往往不是"并行的部分快得超乎寻常"，而是**单核基准 `T(1)` 被某些物理因素拖慢了**，导致这个分母偏大，算出来的加速比虚高。而最主要的物理因素就是缓存。

**cache 是怎么起作用的**

现代 CPU 每个核心都有自己的高速缓存（L1、L2，通常还共享 L3）。缓存的特点是：**容量小、但比主内存（RAM）快得多**——访问 L1 可能是 1 纳秒级，访问主内存要几十上百纳秒，差一两个数量级。

关键点来了：**缓存是每个核心各自带的。当你用更多核心时，可用的缓存总量也随之增加。**

设想一个计算任务，它要处理的数据总量是 100 MB：

- **单核跑**：这一个核心的缓存假设只有 30 MB。100 MB 的数据塞不进去，大量数据只能待在慢速的主内存里。计算过程中 CPU 反复要去主内存取数据（这叫 cache miss，缓存未命中），每次都得等，白白浪费大量时间。于是 `T(1)` 很大。
    
- **8 核跑**：数据被切成 8 份，每个核心只需处理约 12.5 MB。现在每一份都能**完整放进各自的 30 MB 缓存里**了。计算时数据几乎都在高速缓存中，很少再去碰慢速主内存。于是每个核心不光分担了 1/8 的计算量，**还额外享受了"数据全在缓存里"的加速**。
    

这两个效果叠加，就可能让 8 核的总时间少于 `T(1) / 8`，于是 `S(8) > 8`、效率 > 100%。

用个比喻：单核就像一个人在一张小桌子上拼一幅超大拼图，桌子放不下，大部分拼图块只能堆在旁边地上的箱子里，每拼一块都要弯腰去箱子里翻找（慢）。现在来了 8 个人，每人分到一小堆，**恰好每一小堆都能摊在自己面前的桌上**，不用再弯腰翻箱子了。人数变成 8 倍，但因为"不用弯腰"这个额外好处，总速度快了不止 8 倍。

**除了 cache，还有几个次要来源**

缓存是最经典、最主要的原因，但超线性加速偶尔也来自别的地方，顺带一提：

一是内存带宽/NUMA 效应。多核（尤其跨多个 CPU 插槽）时可用的内存带宽也更高，数据供给更快。

二是某些搜索类算法的"运气"。比如并行搜索一个解，多个线程同时从不同位置找，可能某个线程很早就撞见答案，整体提前结束——这类超线性是算法性质带来的，不是硬件，某种程度上带偶然性。

**那到底"合理"吗？该怎么看待它**

分两种情况：

如果你观察到轻微的超线性（效率比如 105%–120%），而且数据规模正好卡在"单核缓存装不下、多核能装下"这个区间，那大概率是**真实且合理**的缓存效应，不用怀疑自己测错了。

但如果效率高得离谱（比如 300%、500%），那就要警惕了，通常说明**基准测试的方式有问题**——最常见的是 `T(1)` 没测准。比如单核那次运行时系统在跑别的东西、或者单核版本用了低效的算法/编译选项、或者单核因为内存不够在疯狂 swap（换页到磁盘，那就慢得离谱了）。这种情况下超线性是"假"的，是分母被污染的假象。

一个更严谨的做法是：报告加速比时说清楚 `T(1)` 是怎么测的。有些论文会用"最优的单核实现"作为基准，而不是"并行代码退化到单核跑"，这样得到的加速比更诚实，也更少出现虚高的超线性。

所以回到你的问题：**大于 100% 合理吗？** —— 温和的超线性，配合能讲通的缓存解释，是合理的、真实的物理现象；夸张的超线性，则多半是基准没设好，值得回头检查 `T(1)`。

判断的关键就是问自己一句：**我的单核基准，是不是被缓存不足（或别的什么）不公平地拖慢了？** 如果是，超线性就有了物理解释;如果连这个都解释不通还快得离谱，那就该查测量方法了。
