# Bash 循环为什么只跑了 `small`？

## 核心问题

脚本里明明设置了：

```bash
SCALES="${SCALES:-small medium large very-large}"
```

输出也显示：

```text
SCALES=small medium large very-large
```

但实际只执行了 `small`，然后直接 `Completed`。

真正原因不是 `SCALES` 变量错了，而是：

> `srun` 可能从 CSV 文件的 stdin 里偷走了后面的行，导致外层 `while read` 没有内容可读。

---

> [!summary]- 核心结论
> 
> 当你写：
> 
> ```bash
> while IFS=, read -r SCALE M N UNKNOWNS; do
>   srun ...
> done < "${SIZE_TABLE}"
> ```
> 
> 整个 `while` 循环的标准输入 stdin 都来自 `${SIZE_TABLE}`。
> 
> 循环内部的命令默认也会继承这个 stdin。
> 
> 所以 `srun` 如果读取 stdin，就可能把 CSV 文件后面的行读掉。
> 
> 修复方式：
> 
> ```bash
> srun ... \
>   < /dev/null \
>   | tee "${LOG}"
> ```
> 
> 这样 `srun` 就不会再读取 CSV 文件，只会从空输入 `/dev/null` 读取。

---

## 现象

原始脚本类似：

```bash
SCALES="${SCALES:-small medium large very-large}"
```

作业输出显示：

```text
SCALES=small medium large very-large
```

但实际执行结果只跑了：

```text
[SCALE] small
Completed
```

没有继续执行：

```text
[SCALE] medium
[SCALE] large
[SCALE] very-large
```

CSV 文件本身是正确的：

```text
scale,m,n,unknowns
small,2240,2240,5017600
medium,3160,3160,9985600
large,4500,4500,20250000
very-large,6400,6400,40960000
```

---

> [!question]- 为什么不是 `SCALES` 变量的问题？
> 
> 因为作业输出已经显示：
> 
> ```text
> SCALES=small medium large very-large
> ```
> 
> 这说明变量确实包含了四个 scale。
> 
> 问题发生在真正读取 CSV 的地方：
> 
> ```bash
> while IFS=, read -r SCALE M N UNKNOWNS; do
>   ...
> done < "${SIZE_TABLE}"
> ```
> 
> 换句话说，`SCALES` 只是配置变量，但真正控制循环继续的是：
> 
> ```bash
> read -r SCALE M N UNKNOWNS
> ```
> 
> 如果 `read` 后面读不到 CSV 行了，循环就会结束。

---

## 根本原因

问题代码模式是：

```bash
while IFS=, read -r SCALE M N UNKNOWNS; do
  ...
  srun ...
done < "${SIZE_TABLE}"
```

这里的关键点是：

> `done < "${SIZE_TABLE}"` 会把整个 `while` 循环的 stdin 绑定到 CSV 文件。

所以循环内部的命令也默认继承这个 stdin。

也就是说，`srun` 看到的 stdin 不是键盘，也不是空输入，而是同一个 CSV 文件。

---

> [!tip]- 核心理解
> 
> 可以把 CSV 文件想象成一条水管。
> 
> 外层 `while read` 本来应该一行一行读取：
> 
> ```text
> small
> medium
> large
> very-large
> ```
> 
> 但是循环内部的 `srun` 也连着同一条水管。
> 
> 如果 `srun` 或 MPI 程序读取 stdin，它可能把后面的内容读走。
> 
> 结果就是：
> 
> ```text
> while read 读到 small
> srun 偷走 medium / large / very-large
> while read 再读时已经没内容
> 循环结束
> ```
> 
> 所以脚本看起来像是只跑了 `small`。

---

## 修复方法

把 `srun` 的 stdin 重定向到 `/dev/null`：

```bash
srun ... \
  < /dev/null \
  | tee "${LOG}"
```

完整结构类似：

```bash
while IFS=, read -r SCALE M N UNKNOWNS; do
  echo "[SCALE] ${SCALE}"

  srun ... \
    < /dev/null \
    | tee "${LOG}"

done < "${SIZE_TABLE}"
```

---

> [!success]- 代码 / 命令
> 
> 推荐写法：
> 
> ```bash
> while IFS=, read -r SCALE M N UNKNOWNS; do
>   echo "[SCALE] ${SCALE}"
> 
>   srun ... \
>     < /dev/null \
>     | tee "${LOG}"
> 
> done < "${SIZE_TABLE}"
> ```
> 
> 整体逻辑：
> 
> - `while read`：负责逐行读取 CSV
>     
> - `${SIZE_TABLE}`：作为外层循环的输入
>     
> - `srun`：负责运行并行程序
>     
> - `< /dev/null`：阻止 `srun` 读取 CSV
>     
> - `tee "${LOG}"`：同时输出到终端和日志文件
>     
> 
> 最容易写错的地方：
> 
> ```bash
> srun ... | tee "${LOG}"
> ```
> 
> 这样 `srun` 仍然可能继承 CSV stdin。
> 
> 应该写成：
> 
> ```bash
> srun ... < /dev/null | tee "${LOG}"
> ```

---

## `/dev/null` 是什么？

`/dev/null` 是 Linux 里的一个特殊文件。

它可以理解为：

> 一个永远为空的输入源。

当你写：

```bash
srun ... < /dev/null
```

意思是：

> 如果 `srun` 想读 stdin，就让它从空文件里读，不要从 CSV 里读。

这样 CSV 文件只会被外层 `while read` 消耗。

---

> [!example]- 示例理解
> 
> 没有 `< /dev/null` 时：
> 
> ```text
> outer loop got: small
> inner command stole: medium
> outer loop got: large
> inner command stole: very-large
> ```
> 
> 外层循环只读到了：
> 
> ```text
> small
> large
> ```
> 
> 因为中间的命令偷走了：
> 
> ```text
> medium
> very-large
> ```
> 
> 加上 `< /dev/null` 后：
> 
> ```text
> outer loop got: small
> inner command stole: <nothing>
> outer loop got: medium
> inner command stole: <nothing>
> outer loop got: large
> inner command stole: <nothing>
> outer loop got: very-large
> inner command stole: <nothing>
> ```
> 
> 这时外层循环可以正常读完整个 CSV。

## 最小复现 Demo

可以写一个 demo 脚本：

```text
scripts/ksp/stdin_loop_demo.sh
```

运行：

```bash
bash scripts/ksp/stdin_loop_demo.sh
```

示例逻辑：

```bash
#!/usr/bin/env bash

cat > /tmp/scales.csv <<EOF
small
medium
large
very-large
EOF

echo "== Without < /dev/null =="
while read -r scale; do
  echo "outer loop got: ${scale}"
  read -r stolen && echo "inner command stole: ${stolen}"
done < /tmp/scales.csv

echo
echo "== With < /dev/null =="
while read -r scale; do
  echo "outer loop got: ${scale}"
  read -r stolen < /dev/null || echo "inner command stole: <nothing>"
done < /tmp/scales.csv
```

---

> [!warning]- 常见误区
> 
> 误区一：以为 `SCALES` 正确，循环就一定会跑完。
> 
> 实际上，真正决定循环能否继续的是 CSV 是否还能被 `read` 读取。
> 
> 误区二：以为只有 `read` 会读取 stdin。
> 
> 实际上，循环内部的很多命令都可能继承 stdin，例如：
> 
> ```text
> srun
> mpirun
> ssh
> python script.py
> bash script.sh
> ```
> 
> 误区三：以为 `tee` 会导致这个问题。
> 
> `tee` 主要处理 stdout，不是根本原因。
> 
> 根本原因是 `srun` 继承了外层循环的 stdin。

## 通用规则

只要看到这种模式：

```bash
while read ...; do
  command_that_might_read_stdin
done < input_file
```

就要警惕：

> 循环内部的命令可能会消耗 `input_file`。

更安全的写法是：

```bash
while read ...; do
  command_that_might_read_stdin < /dev/null
done < input_file
```

对于 HPC / MPI / Slurm 脚本，尤其要注意：

```bash
srun ... < /dev/null
```

或者：

```bash
mpirun ... < /dev/null
```

---

> [!note]- 术语表
> 
> `stdin`
> 
> 标准输入，程序默认读取输入的地方。
> 
> `stdout`
> 
> 标准输出，程序默认打印结果的地方。
> 
> `stderr`
> 
> 标准错误输出，程序默认打印错误信息的地方。
> 
> `/dev/null`
> 
> Linux 中的空设备。作为输入时永远为空，作为输出时会丢弃所有内容。
> 
> `while read`
> 
> Bash 中逐行读取文本的常见写法。
> 
> `srun`
> 
> Slurm 中用于启动并行任务的命令。
> 
> `tee`
> 
> 把输出同时写到终端和文件。

## 面试级回答

如果面试时被问：

> 为什么这个 Bash 循环只跑了一次？

可以回答：

> 因为 `while read ... done < file` 会让整个循环的 stdin 来自这个文件。循环内部的命令也会继承这个 stdin。如果内部命令，比如 `srun`、`mpirun` 或 `ssh` 读取了 stdin，就可能提前消耗掉文件后面的行，导致外层 `read` 没有内容可读，循环提前结束。解决方法是给内部命令加 `< /dev/null`，让它从空输入读取，保护外层循环的输入流。
