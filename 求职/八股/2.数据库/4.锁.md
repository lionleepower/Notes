# MySQL 锁机制（全局锁 / 表级锁 / 行级锁）

## 1. 这个问题在面试中考什么？

主要考察你对 MySQL 锁的**粒度分层**（全局 → 表级 → 行级）以及**行级锁如何解决幻读**的理解，其中间隙锁 / Next-Key Lock 是高频深挖点。

## 2. 重要程度总览

| 知识点 | 重要程度 | 面试要求 |
|---|---|---|
| 全局锁 | 了解即可 | 知道用于全库逻辑备份，及 MVCC 如何改进即可 |
| 表级锁（元数据锁 / 意向锁 / AUTO-INC 锁） | 需要掌握 | 理解各自作用与冲突关系 |
| 行级锁（记录锁 / 间隙锁 / Next-Key Lock / 插入意向锁） | 必须掌握 | 能口述、能区分、能说清如何防幻读 |
| 加锁规则（何时退化） | 了解即可 | 知道唯一索引等值查询会退化即可 |

## 3. 核心知识表格

| 锁 | 粒度 | 核心作用 | 典型场景 | 面试关键词 |
|---|---|---|---|---|
| 全局锁 | 库 | 整库只读，阻塞增删改 | 全库逻辑备份 | FTWRL、Read View、MVCC |
| 元数据锁（MDL） | 表 | 保护表结构，防止 CRUD 时被改结构 | 自动加锁，事务提交才释放 | 隐式、事务结束释放 |
| 意向锁 | 表 | 快速判断表内是否有行被锁 | 加行锁前先加意向锁 | 意向共享/独占、只与表锁冲突 |
| AUTO-INC 锁 | 表 | 保证自增主键连续递增 | 插入不指定主键 | innodb_autoinc_lock_mode |
| 记录锁 | 行 | 锁住单条记录 | 精确锁一行 | Record Lock、共享/排他 |
| 间隙锁 | 行 | 锁住一段范围，防幻读 | 可重复读隔离级别 | Gap Lock、彼此兼容 |
| Next-Key Lock | 行 | 记录锁 + 间隙锁 | RR 下默认加锁单位 | 锁记录 + 锁前面间隙 |
| 插入意向锁 | 行 | 表示想在某区间插入 | 插入被间隙锁阻塞时 | 等待、区间插入 |

## 4. 高频问题整理

### 4.1 全局锁有什么作用？

一句话：让整库进入只读状态，主要用于全库逻辑备份，但可用 MVCC 避免业务停滞。

> [!note]- 了解即可
> 全局锁面试低频，知道它用于全库备份、以及 MVCC 如何改进备份即可，不需深入。

> [!summary]- 核心结论
> 全局锁让整个数据库只读，增删改被阻塞，主要用于全库逻辑备份，保证备份数据与表结构一致。缺陷是备份期间业务无法更新，可用「可重复读 + 事务 + MVCC」改进。

> [!example]- 具体例子
> 直接加全局锁备份：业务只能读不能写，长时间备份会造成业务停滞。
> 改进做法：备份前先开启事务，事务创建一个 Read View，整个备份期间都用这个 Read View。由于 MVCC 支持，其他事务即使更新了数据也不影响这个 Read View，因此业务可正常更新，而备份读到的始终是开启事务那一刻的快照数据。

> [!warning]- 常见误区
> 以为备份一定要锁全库导致业务停滞。实际上支持事务的引擎（如 InnoDB）配合 MVCC 就不必真正加全局锁。

> [!note]- 关键词
> 整库只读、全库逻辑备份、Read View、MVCC、事务快照。

### 4.2 表级锁有哪些？作用是什么？

一句话：主要有元数据锁、意向锁、AUTO-INC 锁三类，分别保护表结构、加速行锁判断、保证自增连续。

> [!info]- 需要掌握
> 表级锁有面试价值，需要理解三种锁各自的作用与冲突关系，尤其是意向锁「快速判断表内是否有行被锁」的目的。

> [!summary]- 核心结论
> 元数据锁（MDL）在 CRUD 时自动加，保护表结构不被并发变更，事务提交后才释放；意向锁是表级锁，用于快速判断表里是否有行被加锁，只与表锁冲突；AUTO-INC 锁保证自增主键连续递增。

> [!example]- 具体例子
> **元数据锁**：一个事务在读写表时，另一个线程想改表结构（ALTER），会被 MDL 阻塞，直到前一事务提交。
> **意向锁**：给某行加独占锁前，先在表级加「意向独占锁」。这样想加表锁的事务只需看有没有意向锁，就能快速知道表内是否有行被锁，无需逐行检查。普通 select 走 MVCC，是无锁的（但可用 `select ... for share` / `for update` 主动加行锁）。
> **AUTO-INC 锁**：插入时不指定主键，数据库自动赋递增值。传统 AUTO-INC 锁要等整条插入语句执行完才释放，批量插入时会阻塞其他插入，影响性能。

> [!note]- AUTO-INC 锁控制（了解即可）
> 通过系统变量 innodb_autoinc_lock_mode 控制：
> - = 0：传统 AUTO-INC 锁，语句执行结束才释放；
> - = 1：普通 insert 申请后立即释放，`insert ... select` 等批量插入要到语句结束才释放；
> - = 2：轻量级锁，申请到自增值后立即释放，并发性能最高。
>
> 但 mode = 2 搭配 binlog_format = statement 时，主从复制会出现数据不一致。解决办法：binlog_format 设为 row，binlog 记录主库分配的实际自增值，从库照抄，既高并发又一致。

> [!warning]- 常见误区
> 1. 以为意向锁会和行级共享/独占锁冲突——不会，意向锁之间也不冲突，只与表级共享/独占锁冲突。
> 2. 以为普通 select 会加行锁——普通 select 走 MVCC 无锁。
> 3. 以为 MDL 需要手动加——它是自动隐式加的。

> [!note]- 关键词
> 元数据锁 MDL、意向共享/独占锁、快速判断、AUTO-INC 锁、innodb_autoinc_lock_mode、binlog_format = row。

### 4.3 行级锁有哪些？作用是什么？（重点）

一句话：记录锁锁单行，间隙锁锁范围防幻读，Next-Key Lock 是两者组合，插入意向锁表示想在区间插入。

> [!important]- 必须掌握
> 行级锁是 MySQL 锁的面试核心，必须能说出四种锁、能解释间隙锁如何解决可重复读下的幻读、能说清 Next-Key Lock 的组成。

> [!summary]- 核心结论
> 记录锁锁住单条记录（分共享/排他）；间隙锁只存在于可重复读隔离级别，锁住一段区间以防幻读，间隙锁之间彼此兼容不互斥；Next-Key Lock = 记录锁 + 间隙锁，既锁记录本身又锁记录前面的间隙；插入意向锁是插入时若命中他人间隙锁则进入等待状态生成的锁。

> [!question]- 面试怎么答
> MySQL 的行级锁主要有四种。记录锁（Record Lock）锁住单条记录，分共享锁和排他锁。间隙锁（Gap Lock）只在可重复读隔离级别下存在，锁住一段开区间，用来防止其他事务在这段范围里插入新记录，从而解决幻读；间隙锁之间是兼容的，多个事务可以同时持有重叠的间隙锁。Next-Key Lock 是记录锁加间隙锁的组合，既锁住记录本身，又锁住记录前面的间隙，是 RR 下默认的加锁单位。插入意向锁则是：一个事务插入记录时会先判断插入位置是否落在别人的间隙锁范围内，如果是就阻塞并生成一个插入意向锁，表示我想在这个区间插入但正在等待。

> [!example]- 具体例子
> 表中有主键 id = 5, 10。事务 A 执行 `select * from t where id > 5 and id < 10 for update`，会在 (5, 10) 加间隙锁。此时事务 B 想 `insert id = 7`，会先判断 7 落在别人的间隙锁里，于是阻塞并生成插入意向锁，直到事务 A 提交释放间隙锁后才能插入——这样就防止了「幻读」。

> [!warning]- 常见误区
> 1. 以为间隙锁之间会互斥——间隙锁彼此兼容，两个事务可同时持有包含共同间隙的间隙锁。
> 2. 以为间隙锁在所有隔离级别都存在——只存在于可重复读（RR）。
> 3. 把 Next-Key Lock 当成独立第三种锁——它是「记录锁 + 间隙锁」的组合。
> 4. 以为插入意向锁会主动阻塞别人——它本身是被阻塞时生成的「等待标记」。

> [!note]- 关键词
> Record Lock、Gap Lock、间隙锁兼容、Next-Key Lock、临键锁、插入意向锁、可重复读、幻读。

### 4.4 MySQL 是怎么加锁的？（退化规则）

一句话：核心是记住「唯一索引等值查询会退化」这一条主线，其余按记录是否存在、索引是否唯一区分。

> [!note]- 了解即可
> 加锁退化规则细节多、易混，面试低频深挖。掌握「唯一索引等值查询命中则退化为记录锁、未命中则退化为间隙锁」这条主线即可。

> [!summary]- 核心结论
> Next-Key Lock 在特定条件下会退化为更小的锁：唯一索引等值查询命中记录退化为记录锁，未命中退化为间隙锁；非唯一索引等值查询会在 Next-Key Lock 基础上额外处理；范围查询一般不退化。

> [!example]- 加锁退化对照
>
> | 查询方式 | 记录是否存在 | 加锁结果 |
> |---|---|---|
> | 唯一索引等值查询 | 存在 | 退化为记录锁 |
> | 唯一索引等值查询 | 不存在 | 退化为间隙锁 |
> | 非唯一索引等值查询 | 存在 | Next-Key Lock + 额外间隙锁 |
> | 非唯一索引等值查询 | 不存在 | Next-Key Lock 退化为间隙锁 |
> | 非唯一索引范围查询 | — | Next-Key Lock 不退化 |

> [!note]- 关键词
> 退化、唯一索引、非唯一索引、等值查询、范围查询、记录存在与否。

## 5. 对比关系或流程梳理

锁粒度从大到小：**全局锁（库）→ 表级锁（表）→ 行级锁（行）**。粒度越大越省内存、并发越低；粒度越小并发越高、开销越大。

- 全局锁：备份场景，可被 MVCC 替代。
- 表级锁：MDL 保结构、意向锁做「有没有行被锁」的快速判断、AUTO-INC 保自增。
- 行级锁：记录锁锁点、间隙锁锁线（区间）、Next-Key 锁「点 + 前面的线」、插入意向锁是插入时的等待标记。

## 6. 常见误区

> [!warning]- 汇总
> - 间隙锁之间**兼容**，不互斥；只用来防插入。
> - 间隙锁只在**可重复读**隔离级别存在。
> - 意向锁只与**表锁**冲突，不与行锁冲突，意向锁之间也不冲突。
> - 普通 select 走 **MVCC 无锁**，加锁需显式 `for update` / `for share`。
> - Next-Key Lock 不是第三种独立锁，是**记录锁 + 间隙锁**。
> - AUTO-INC 的 mode = 2 高并发，但需搭配 **binlog_format = row** 才不会主从不一致。

## 7. 面试口述版答案

> [!question]- 「说说 MySQL 有哪些锁」
> MySQL 的锁按粒度分三层。最粗的是全局锁，让整库只读，主要用于全库逻辑备份，不过现在一般用可重复读事务加 MVCC 来做备份，避免锁库。中间是表级锁，常见的有元数据锁（保护表结构、CRUD 时自动加、事务提交才释放）、意向锁（表级锁，用来快速判断表里有没有行被锁）、以及 AUTO-INC 锁（保证自增主键连续）。最细的是行级锁，也是重点：记录锁锁单行；间隙锁只在可重复读下存在，锁一段区间来防幻读，而且间隙锁之间是兼容的；Next-Key Lock 是记录锁加间隙锁的组合，是 RR 下默认的加锁单位；插入意向锁是插入时命中别人间隙锁而进入等待时生成的锁。加锁还有退化规则，比如唯一索引等值查询命中会退化成记录锁、没命中退化成间隙锁。

## 9. 最终速记版

> [!tip]- 一句话速记
> **三层粒度**：全局（备份，MVCC 可替）→ 表级（MDL 保结构 / 意向锁快速判断 / AUTO-INC 保自增）→ 行级（记录锁点 / 间隙锁线 / Next-Key 点+线 / 插入意向锁等待）。
> **两个高频点**：间隙锁只在 RR 且彼此兼容、防幻读；唯一索引等值查询命中退记录锁、未命中退间隙锁。
