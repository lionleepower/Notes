# MySQL 事务与隔离级别（ACID / 并发问题 / 隔离级别 / MVCC）

## 1. 这个问题在面试中考什么？

考四层递进：事务是什么（ACID 及其实现）→ 并发会出什么问题（脏读/不可重复读/幻读）→ 靠什么隔离（四个隔离级别）→ InnoDB 怎么实现的（MVCC + next-key lock）。这是数据库面试的绝对高频重灾区。

## 2. 重要程度总览

|知识点|重要程度|一句话|
|---|---|---|
|ACID 四大特性|必须掌握|原子/一致/隔离/持久，以及各由什么日志实现|
|并发三大问题|必须掌握|脏读 / 不可重复读 / 幻读的区别|
|四个隔离级别|必须掌握|读未提交→读提交→可重复读→串行化|
|各级别对应现象|必须掌握|哪个级别防住哪个问题|
|MVCC 实现原理|必须掌握|Read View + 隐藏列 + 版本可见性判断|
|幻读如何解决|必须掌握|快照读靠 MVCC，当前读靠 next-key lock|
|读提交如何实现|必须掌握|每次读都生成新的 Read View|

## 3. 事务的四大特性（ACID）是什么？

一句话：原子性、一致性、隔离性、持久性，四者共同保证事务「要么全成、要么全败且不丢」。

> [!important]- 必须掌握
> 事务面试第一题，必须能说出四个特性各是什么，并能答出「每个特性由什么机制实现」——这是区分背概念和真理解的关键。

> [!summary]- 核心结论
> 原子性（Atomicity）：事务是不可分割的最小单元，全部成功或全部回滚；一致性（Consistency）：数据库从一个一致状态转到另一个一致状态；隔离性（Isolation）：事务提交前的修改对其他事务不可见；持久性（Durability）：一旦提交，修改永久保存、崩溃也不丢。

> [!question]- 面试怎么答
> 事务有四大特性，简称 ACID。原子性指事务内所有操作要么全部提交成功、要么全部回滚，不会只执行一部分；一致性指数据库总是从一个一致状态转换到另一个一致状态；隔离性指一个事务提交前的修改对其他事务不可见；持久性指事务一旦提交，修改就永久落盘，即使系统崩溃也不会丢失。实现上，原子性靠 undo log，持久性靠 redo log，隔离性靠 MVCC 或锁，而一致性是由前面三个特性共同保证的最终目的。

> [!example]- 具体例子
> 转账 A→B 100 元：原子性保证「A 扣钱」和「B 加钱」同时成功或同时失败；一致性保证转账前后总额不变；隔离性保证转账中途别的事务看不到「A 已扣、B 未加」的中间态；持久性保证转账成功后即使宕机也不会退回。

> [!warning]- 常见误区
> 
> - 把一致性和另外三个并列——其实一致性是**目的**，靠原子性+隔离性+持久性共同实现。
> - 记反实现日志：**原子性→undo log**（回滚），**持久性→redo log**（崩溃恢复），别搞反。

> [!note]- 关键词
> 原子性/undo log、持久性/redo log、隔离性/MVCC 或锁、一致性是目的

## 4. 并发事务会出现什么问题？

一句话：脏读（读到未提交）、不可重复读（同数据两次读不同，改）、幻读（同查询两次行数不同，增）。

> [!important]- 必须掌握
> 必须能一句话精准区分三者，尤其「不可重复读 vs 幻读」是高频追问点：前者针对 update、后者针对 insert。

> [!summary]- 核心结论
> 脏读：读到了其他事务**未提交**的数据（可能被回滚，即读到不存在的数据）；不可重复读：同一事务内前后读同一批数据结果不同（被其他事务**更新**并提交所致，针对 update）；幻读：同一事务内前后查询的**记录条数**不同（被其他事务**插入**新行所致，针对 insert）。

> [!question]- 面试怎么答
> 并发事务主要有三个问题。脏读是读到了其他事务还没提交的数据，这些数据可能会被回滚，等于读到了不存在的数据；不可重复读是在同一个事务里，两次读同一批数据的值不一样，通常是因为中间有别的事务更新并提交了，针对的是更新操作；幻读是在同一个事务里，两次执行同样的查询，第二次多出来或少了一些行，通常是因为别的事务插入了新记录，针对的是插入操作。核心区别就是：不可重复读关注同一行的值变了，幻读关注查出来的行数变了。

> [!warning]- 常见误区
> **不可重复读和幻读最容易混**：抓住「值变了 = 不可重复读（update）」「行数变了 = 幻读（insert）」这一条就不会错。

> [!note]- 关键词
> 脏读（未提交）、不可重复读（update/值变）、幻读（insert/行数变）

## 5. MySQL 的事务隔离级别有哪些？

一句话：读未提交 → 读提交 → 可重复读（InnoDB 默认）→ 串行化，隔离性依次增强、并发性依次降低。

> [!important]- 必须掌握
> 必须能背出四个级别的名称和含义，并牢记 **InnoDB 默认是可重复读（RR）**。

> [!summary]- 核心结论
> 读未提交（Read Uncommitted）：事务未提交的变更就能被别的事务看到；读提交（Read Committed）：事务提交后变更才能被看到；可重复读（Repeatable Read）：事务执行期间看到的数据始终和事务启动时一致，是 **InnoDB 默认级别**；串行化（Serializable）：对记录加读写锁，读写冲突时后来的事务必须等前一个执行完。

> [!example]- 具体例子
> 同一条数据被两个事务操作：RC 下事务 B 提交后事务 A 立刻能读到新值；RR 下事务 A 整个生命周期都读它启动时的快照，读不到 B 的提交；Serializable 下两事务直接串行排队，几乎无并发。

> [!warning]- 常见误区
> 很多人记成「大多数数据库默认 RC」——**Oracle/SQL Server 默认 RC，但 MySQL InnoDB 默认 RR**，问的是 MySQL 时别答错。

> [!note]- 关键词
> RU、RC、RR（InnoDB 默认）、Serializable、隔离性↑并发性↓

## 6. 不同隔离级别下会发生哪些现象？

一句话：级别越高防住的问题越多，串行化全防住但性能最差。

> [!important]- 必须掌握
> 高频「连连看」题，必须能背出下表，并知道解决各问题应升到哪个级别。

> [!summary]- 核心结论
> 隔离级别与并发问题的对应关系见下表；解决脏读升到读提交及以上，解决不可重复读升到可重复读，解决幻读理论上升到串行化——但串行化性能极差，实际不推荐，InnoDB 在 RR 下已用 MVCC + next-key lock 很大程度避免了幻读。

> [!example]- 对照表
> 
> |隔离级别|脏读|不可重复读|幻读|
> |---|---|---|---|
> |读未提交 RU|可能|可能|可能|
> |读提交 RC|不会|可能|可能|
> |可重复读 RR|不会|不会|可能（InnoDB 已基本避免）|
> |串行化 Serializable|不会|不会|不会|

> [!warning]- 常见误区
> 别为了解决幻读就无脑升到串行化——串行化并发性能很差；InnoDB 在默认 RR 下已通过 MVCC（快照读）+ next-key lock（当前读）基本解决了幻读。

> [!note]- 关键词
> RU 全有、RC 防脏读、RR 防不可重复读、Serializable 全防、性能代价

## 7. MVCC 的实现原理？

一句话：靠 Read View + 聚簇索引隐藏列（trx_id / roll_pointer），按版本可见性规则决定每条记录读哪个版本。

> [!important]- 必须掌握
> MVCC 是 InnoDB 的核心，也是区分「会用」和「懂原理」的分水岭，必须能讲清 Read View 四字段和可见性判断三种情况。

> [!summary]- 核心结论
> Read View 有四个字段：`m_ids`（创建时的活跃事务 id 列表）、`min_trx_id`（活跃事务最小 id）、`max_trx_id`（下一个要分配的事务 id，即全局最大 +1）、`creator_trx_id`（创建该 Read View 的事务 id）。聚簇索引每条记录有两个隐藏列：`trx_id`（改动它的事务 id）和 `roll_pointer`（指向 undo log 里的旧版本，形成版本链）。访问记录时按 trx_id 与 Read View 的关系判断该版本是否可见。

> [!question]- 面试怎么答
> MVCC 是多版本并发控制，靠 Read View 和记录的隐藏列实现。每条聚簇索引记录有 trx_id 和 roll_pointer 两个隐藏列，trx_id 记录改动它的事务号，roll_pointer 指向 undo log 里的旧版本，多个旧版本串成一条版本链。事务读数据时会拿一个 Read View，里面记了创建时的活跃事务列表、最小事务 id、下一个事务 id 和自己的事务 id。判断某个版本可不可见的规则是：如果记录的 trx_id 小于 min_trx_id，说明是创建 Read View 前就已提交的，可见；如果大于等于 max_trx_id，说明是之后才启动的事务生成的，不可见；如果在两者之间，就看它在不在活跃列表 m_ids 里，在就说明还没提交、不可见，不在就说明已提交、可见。不可见时就顺着 roll_pointer 找旧版本。

> [!example]- 可见性判断三种情况
> 
> - `trx_id < min_trx_id`：Read View 创建前已提交 → **可见**。
> - `trx_id ≥ max_trx_id`：Read View 创建后才启动 → **不可见**。
> - `min_trx_id ≤ trx_id < max_trx_id`：再看是否在 `m_ids` 中——在（仍活跃未提交）→ **不可见**；不在（已提交）→ **可见**。
> - 另：事务自己的更新记录总是可见。

> [!warning]- 常见误区
> 
> - Read View 生成时机决定隔离级别：**RC 每次快照读都新建 Read View，RR 只在第一次快照读时建一次并复用**——这正是两者行为差异的根因。
> - `max_trx_id` 是「下一个要分配的 id」（全局最大 +1），不是当前最大 id。

> [!note]- 关键词
> Read View 四字段、trx_id/roll_pointer 隐藏列、undo 版本链、可见性三判断

## 8. 幻读是如何解决的？

一句话：快照读靠 MVCC，当前读靠 next-key lock（记录锁 + 间隙锁）。

> [!important]- 必须掌握
> RR 如何处理幻读是高频追问，必须能区分「快照读 vs 当前读」两条路径，并知道 RR 并未彻底解决幻读。

> [!summary]- 核心结论
> 快照读（普通 `select`）：靠 MVCC，RR 下整个事务看到的都是启动时的快照，别人中途插入的数据查不出来；当前读（`select ... for update`、`update`、`delete` 等）：靠 next-key lock（记录锁 + 间隙锁），别人想在锁范围内插入会被阻塞。

> [!example]- MVCC 与当前读失效场景
> RR 并没有**彻底**解决幻读，两种失效情况：
> 
> - **快照读失效**：事务 A 更新了一条事务 B 插入的记录后，A 前后两次查询条目就不一样了（更新会让该行进入 A 的版本视图），发生幻读。
> - **当前读失效**：事务开启后先做快照读，期间别的事务插入了记录，之后 A 再用当前读查询，两次结果条目不同，发生幻读。

> [!question]- 面试怎么答
> 幻读的解决分两种读。普通 select 是快照读，通过 MVCC 解决：可重复读级别下事务看到的数据一直是启动时的快照，别人中途插入的行查不出来。select ... for update 这类是当前读，通过 next-key lock 解决：它会加记录锁加间隙锁，别的事务想在这个范围内插入新记录会被阻塞。不过 RR 并没有彻底根除幻读，比如先快照读、别人插入、再当前读，或者事务 A 更新了 B 插入的行，都会露出幻读，所以最佳实践是开启事务后尽早执行 select ... for update 提前加 next-key lock。

> [!warning]- 常见误区
> 说「RR 完全解决了幻读」是不准确的——**只是很大程度避免**，上面两种场景仍会出现幻读；实践中应尽早用当前读加锁。

> [!note]- 关键词
> 快照读/MVCC、当前读/next-key lock（记录锁+间隙锁）、RR 未彻底解决、尽早 for update

## 9. 读提交（RC）是怎么实现的？

一句话：每次读取数据都重新生成一个 Read View。

> [!important]- 必须掌握
> 与 RR 对照理解即可，核心就一句话：RC 每次读都新建 Read View。

> [!summary]- 核心结论
> RC 隔离级别下，每次读取数据时都会生成一个**新的** Read View。因此同一事务内多次读同一条数据，若中间别的事务修改并提交了，前后两次读到的结果会不一致——这正是 RC 会出现不可重复读的原因。

> [!warning]- 常见误区
> RC 与 RR 的唯一实现差异就在 Read View 生成时机：**RC 每次读新建**，**RR 首次读建一次后整事务复用**。这一点几乎必被追问。

> [!note]- 关键词
> 每次读新建 Read View、对比 RR 复用、不可重复读来源

## 10. 最终速记版

> [!tip]- 一分钟速记
> 
> - **ACID**：原子(undo)、持久(redo)、隔离(MVCC/锁)，一致性是三者共同实现的目的。
> - **三大问题**：脏读(读未提交)、不可重复读(update/值变)、幻读(insert/行数变)。
> - **四级别**：RU / RC / RR(InnoDB 默认) / Serializable，隔离↑并发↓。
> - **防住谁**：RC 防脏读，RR 再防不可重复读，Serializable 全防。
> - **MVCC**：Read View 四字段 + trx_id/roll_pointer 隐藏列 + 可见性三判断。
> - **Read View 时机**：RC 每次读新建，RR 首次读建一次复用。
> - **幻读**：快照读→MVCC，当前读→next-key lock；RR 未彻底根除。
