# HTTP 面试常见题

## 1. 这个问题在面试中考什么？

> [!summary]- 核心结论  
> HTTP 面试主要考察四类能力：协议基础、安全机制、性能演进、Web 攻击防护。
> 
> 必须能解释 HTTP 与 HTTPS 的区别、TLS 握手过程、常见状态码、缓存机制、HTTP 各版本差异、GET/POST 区别，以及 XSS、CSRF、中间人攻击的防范思路。

> [!note]- 高频关键词  
> HTTP、HTTPS、TLS、状态码、缓存、长连接、队头阻塞、多路复用、QUIC、GET、POST、RPC、XSS、CSRF、中间人攻击

## 3. HTTP 和 HTTPS 有什么区别？

> [!important]- 必须掌握  
> 这是 HTTP 面试中最高频的基础题。必须能从安全性、端口、证书、连接过程、性能开销几个角度回答。

> [!summary]- 核心结论  
> HTTP 是明文传输协议，数据在网络中可以被窃听、篡改和冒充。
> 
> HTTPS 不是新协议，而是 `HTTP + SSL/TLS`，通过 TLS 提供加密、身份认证和完整性校验。

> [!question]- 面试怎么答  
> HTTP 和 HTTPS 最大区别在于安全性。HTTP 明文传输，默认端口是 80；HTTPS 基于 SSL/TLS，默认端口是 443，会通过证书验证服务器身份，并对传输数据进行加密。
> 
> HTTPS 比 HTTP 多了 TLS 握手和证书校验过程，所以连接建立成本更高，也会消耗更多服务器资源。但它能解决明文传输带来的窃听、篡改和冒充问题。

> [!example]- HTTP 与 HTTPS 对比
> 
> |对比项|HTTP|HTTPS|
> |---|---|---|
> |安全性|明文传输|加密传输|
> |默认端口|80|443|
> |是否需要证书|不需要|需要 CA 证书|
> |底层关系|基于 TCP|基于 TCP + TLS|
> |数据完整性|容易被篡改|TLS 提供完整性校验|
> |性能开销|较低|多 TLS 握手和加解密开销|
> |典型场景|普通非敏感页面|登录、支付、接口通信|

> [!warning]- 常见误区  
> HTTPS 不是绝对不可能被攻击，而是大幅提高了攻击成本。
> 
> HTTPS 的安全依赖证书链、TLS 配置、客户端是否信任正确证书。如果用户主动信任伪造证书，仍可能被中间人攻击。

> [!note]- 关键词  
> 明文传输、TLS、CA 证书、加密、认证、完整性、80、443

## 4. HTTPS 的加密与认证过程是什么？

> [!important]- 必须掌握  
> 这是 HTTPS 的核心问题。面试中不一定要求背完整报文，但必须能讲清楚：协商参数、验证证书、生成会话密钥、后续使用对称加密通信。

> [!summary]- 核心结论  
> HTTPS 握手的核心目标是：验证服务器身份，并安全协商出一个会话密钥。
> 
> 非对称加密主要用于身份认证和密钥协商；真正传输 HTTP 数据时，主要使用对称加密，因为对称加密效率更高。

> [!question]- 面试怎么答  
> HTTPS 建立连接时，客户端先发送 `ClientHello`，告诉服务端支持的 TLS 版本、随机数和密码套件。服务端返回 `ServerHello`，确认 TLS 版本、密码套件、服务端随机数，并发送数字证书。
> 
> 客户端用本地 CA 公钥验证证书是否合法，验证通过后取出证书中的服务端公钥，生成一个 `pre-master key` 并用服务端公钥加密发送给服务端。之后客户端和服务端根据客户端随机数、服务端随机数和 `pre-master key` 生成会话密钥。
> 
> 握手结束后，双方使用会话密钥进行对称加密通信。

> [!example]- TLS 握手流程
> 
> |阶段|发送方|核心内容|目的|
> |---|---|---|---|
> |ClientHello|客户端|TLS 版本、Client Random、密码套件列表|发起协商|
> |ServerHello|服务端|TLS 版本、Server Random、选定密码套件、数字证书|确认协商参数并提供身份|
> |客户端验证证书|客户端|使用 CA 公钥验证证书|确认服务端身份|
> |客户端发送密钥材料|客户端|用服务端公钥加密 `pre-master key`|安全传递密钥材料|
> |生成会话密钥|双方|Client Random + Server Random + pre-master key|生成对称加密密钥|
> |握手完成|双方|Finished 消息摘要校验|确认握手未被篡改|
> |加密通信|双方|使用会话密钥加密 HTTP 数据|传输业务数据|

> [!tip]- 为什么不全程使用非对称加密？  
> 非对称加密计算成本高，不适合大量数据传输。
> 
> HTTPS 的设计是：用非对称加密解决“安全交换密钥”和“身份认证”问题，再用对称加密解决“高效传输数据”问题。

> [!warning]- 常见误区  
> 不要说 HTTPS 全程都使用非对称加密。
> 
> 更准确的说法是：握手阶段使用非对称加密、证书认证和密钥协商，数据传输阶段主要使用对称加密。

> [!note]- 关键词  
> ClientHello、ServerHello、CA、数字证书、公钥、私钥、pre-master key、会话密钥、对称加密、非对称加密

## 5. HTTPS 一定安全吗？

> [!important]- 需要掌握  
> 需要理解 HTTPS 的安全边界。面试中常用于考察证书信任链和中间人攻击。

> [!summary]- 核心结论  
> HTTPS 协议本身提供加密、认证和完整性保护，但并不代表所有 HTTPS 连接都绝对安全。
> 
> 如果用户接受了伪造证书，或者设备被恶意安装了根证书，中间人仍可能解密和监听通信。

> [!question]- 面试怎么答  
> HTTPS 本身目前仍然是安全通信的主流方案，但它依赖证书验证。如果中间人给客户端发送伪造证书，正常情况下浏览器会提示证书不可信。
> 
> 如果用户忽略警告继续访问，或者客户端系统被导入了恶意根证书，那么客户端就会信任中间人的证书，后续 HTTPS 通信就可能被中间人监听和篡改。这不是 HTTPS 协议本身被攻破，而是信任链被破坏。

> [!example]- 中间人伪造证书场景  
> 用户访问 `https://bank.com`。
> 
> 中间人拦截请求，给用户返回一个伪造的 `bank.com` 证书。
> 
> 浏览器发现证书不被可信 CA 签发，于是提示风险。
> 
> 如果用户点击“继续访问”，浏览器就会接受伪造证书，中间人可以分别和客户端、服务端建立两条 TLS 连接，从而监听通信内容。

> [!warning]- 常见误区  
> HTTPS 不安全的常见原因不是 TLS 被轻易破解，而是用户信任了错误证书，或者客户端环境被污染。
> 
> 不要把“用户忽略证书警告”说成“HTTPS 协议不安全”。

> [!note]- 关键词  
> 证书信任链、CA、伪造证书、恶意根证书、中间人攻击、浏览器警告

## 6. HTTP 状态码的含义是什么？

> [!important]- 必须掌握  
> 状态码是 HTTP 面试高频基础题。必须能按类别说明，并记住常见状态码。

> [!summary]- 核心结论  
> HTTP 状态码用于表示服务器对请求的处理结果。
> 
> 可以按首位数字分类：`1xx` 信息提示，`2xx` 成功，`3xx` 重定向，`4xx` 客户端错误，`5xx` 服务端错误。

> [!question]- 面试怎么答  
> HTTP 状态码分为五类。`1xx` 表示请求处理中，实际使用较少；`2xx` 表示请求成功；`3xx` 表示重定向或缓存相关；`4xx` 表示客户端请求有问题；`5xx` 表示服务器处理请求时出错。
> 
> 高频状态码包括 `200`、`301`、`302`、`304`、`400`、`403`、`404`、`500`、`502`、`503`、`504`。

> [!example]- 状态码分类表
> 
> |分类|含义|常见状态码|场景|
> |---|---|---|---|
> |1xx|信息提示|100、101|请求继续、协议切换|
> |2xx|成功|200、204、206|请求成功、无内容、部分内容|
> |3xx|重定向|301、302、304|永久重定向、临时重定向、缓存未修改|
> |4xx|客户端错误|400、403、404|请求语法错误、无权限、资源不存在|
> |5xx|服务端错误|500、502、503、504、505|程序错误、网关错误、服务不可用、网关超时|

> [!note]- 高频状态码
> 
> |状态码|含义|说明|
> |---|---|---|
> |100|Continue|服务器收到请求第一部分，客户端可继续发送|
> |101|Switching Protocols|服务器同意切换协议|
> |200|OK|请求成功|
> |204|No Content|请求成功，但响应体为空|
> |206|Partial Content|部分内容，常用于断点续传|
> |301|Moved Permanently|永久重定向|
> |302|Found|临时重定向|
> |304|Not Modified|资源未修改，可使用缓存|
> |400|Bad Request|请求格式错误|
> |403|Forbidden|服务器拒绝访问|
> |404|Not Found|资源不存在|
> |500|Internal Server Error|服务器内部错误|
> |501|Not Implemented|服务器不支持该功能|
> |502|Bad Gateway|网关或代理访问上游服务器失败|
> |503|Service Unavailable|服务暂时不可用|
> |504|Gateway Timeout|网关等待上游服务器超时|
> |505|HTTP Version Not Supported|不支持 HTTP 版本|

> [!warning]- 常见误区  
> `301` 和 `302` 不是服务器直接“跳转页面”，而是服务器返回状态码和 `Location` 响应头，由浏览器发起新的请求。
> 
> `304` 不代表服务器返回了完整资源，而是告诉客户端本地缓存仍然可用。

> [!note]- 关键词  
> 1xx、2xx、3xx、4xx、5xx、Location、304、缓存、重定向、网关错误

## 7. HTTP 缓存有哪些实现方式？

> [!important]- 需要掌握  
> HTTP 缓存是前端、后端、网络面试都常考的内容。重点掌握强缓存和协商缓存的区别。

> [!summary]- 核心结论  
> HTTP 缓存主要分为强缓存和协商缓存。
> 
> 强缓存由浏览器根据缓存过期时间自行判断是否使用缓存；协商缓存需要向服务器确认资源是否发生变化，常见返回状态码是 `304 Not Modified`。

> [!question]- 面试怎么答  
> HTTP 缓存分为强缓存和协商缓存。强缓存命中时，浏览器直接使用本地缓存，不会向服务器发送请求。协商缓存会向服务器发送请求，由服务器判断资源是否变化，如果没有变化就返回 `304`，浏览器继续使用本地缓存。
> 
> 强缓存常见字段有 `Expires` 和 `Cache-Control`；协商缓存常见字段有 `Last-Modified`、`If-Modified-Since`、`ETag`、`If-None-Match`。

> [!example]- 强缓存和协商缓存对比
> 
> |类型|是否请求服务器|常见字段|返回结果|主动判断方|
> |---|---|---|---|---|
> |强缓存|不请求|`Expires`、`Cache-Control`|直接使用本地缓存|浏览器|
> |协商缓存|请求服务器|`Last-Modified`、`ETag`|`304 Not Modified` 或返回新资源|服务器|

> [!tip]- 为什么需要协商缓存？  
> 强缓存只看过期时间，无法知道资源是否真的变化。
> 
> 协商缓存通过向服务器确认资源版本，能在保证资源正确性的同时减少传输开销。

> [!warning]- 常见误区  
> `304` 不是请求失败，而是缓存命中。
> 
> 强缓存命中时通常不会请求服务器；协商缓存一定会请求服务器，只是不一定返回完整资源。

> [!note]- 关键词  
> 强缓存、协商缓存、Expires、Cache-Control、Last-Modified、If-Modified-Since、ETag、If-None-Match、304

## 8. HTTP/1.0、HTTP/1.1、HTTP/2.0 和 HTTP/3.0 有什么区别？

> [!important]- 必须掌握  
> 这是 HTTP 性能演进类高频题。必须能围绕连接复用、队头阻塞、多路复用、传输协议变化回答。

> [!summary]- 核心结论  
> HTTP 的版本演进主要是在解决连接开销、传输效率和队头阻塞问题。
> 
> HTTP/1.0 默认短连接；HTTP/1.1 引入长连接和管道化；HTTP/2 使用二进制帧、多路复用和头部压缩；HTTP/3 基于 QUIC 和 UDP，进一步解决 TCP 层队头阻塞和连接迁移问题。

> [!question]- 面试怎么答  
> HTTP/1.0 每次请求通常都要建立 TCP 连接，连接开销大。HTTP/1.1 默认支持长连接，可以复用 TCP 连接，并支持管道化和断点续传。
> 
> HTTP/2 改成二进制帧格式，在同一个 TCP 连接上实现多路复用，还支持头部压缩和服务端推送。但 HTTP/2 仍然基于 TCP，如果 TCP 层丢包，整个连接仍可能被阻塞。
> 
> HTTP/3 基于 UDP 实现 QUIC，在应用层实现可靠传输、多路复用、拥塞控制和 TLS 集成，多个 Stream 之间相互独立，因此能减少队头阻塞，并支持连接迁移。

> [!example]- 版本对比表
> 
> |版本|底层协议|连接方式|核心改进|主要问题|
> |---|---|---|---|---|
> |HTTP/1.0|TCP|默认短连接|基础请求响应模型|每次请求建连开销大，队头阻塞明显|
> |HTTP/1.1|TCP|默认长连接|Keep-Alive、管道化、更多缓存控制、Range|管道化仍有应用层队头阻塞|
> |HTTP/2.0|TCP|单连接多路复用|二进制帧、头部压缩、多路复用、Server Push|TCP 丢包会导致连接级队头阻塞|
> |HTTP/3.0|UDP + QUIC|QUIC 连接|0-RTT、连接迁移、Stream 独立、多路复用|部署和兼容成本更高|

---

### 8.1 HTTP/1.0 的特点是什么？

> [!note]- 了解即可  
> HTTP/1.0 主要用于理解 HTTP 演进背景。知道它默认短连接、连接开销大、缓存能力较基础即可。

> [!summary]- 核心结论  
> HTTP/1.0 默认无连接，每次请求通常都要新建 TCP 连接。
> 
> 它可以通过 `keep-alive` 参数建立长连接，但不是默认行为。

> [!example]- 典型问题  
> 一个网页有 HTML、CSS、JS、图片等多个资源。
> 
> 如果每个资源都新建一次 TCP 连接，就会产生大量三次握手和四次挥手开销。

> [!warning]- 常见误区  
> HTTP/1.0 不是完全不能长连接，而是默认不使用长连接，需要额外配置 `keep-alive`。

---

### 8.2 HTTP/1.1 的特点是什么？

> [!important]- 需要掌握  
> HTTP/1.1 是实际工程中长期使用的主流版本，必须掌握长连接、管道化、缓存和 Range 请求。

> [!summary]- 核心结论  
> HTTP/1.1 默认支持长连接，减少了 TCP 连接重复建立和断开的开销。
> 
> 它还支持管道化、更多缓存控制策略和 Range 断点续传。

> [!example]- Range 断点续传  
> 下载一个大文件时，如果中途断开，客户端可以通过 `Range` 请求资源的一部分。
> 
> 服务端返回 `206 Partial Content`，只传输指定范围的数据。

> [!warning]- 常见误区  
> 管道化允许连续发送多个请求，但响应仍需要按顺序返回。
> 
> 如果前一个响应很慢，后面的响应仍可能被阻塞，所以它没有彻底解决队头阻塞。

---

### 8.3 HTTP/2.0 的特点是什么？

> [!important]- 必须掌握  
> HTTP/2 是现代 HTTP 性能优化的重要节点。必须掌握二进制帧、多路复用、头部压缩和 TCP 队头阻塞问题。

> [!summary]- 核心结论  
> HTTP/2 把 HTTP 消息拆成二进制帧，并在同一个 TCP 连接上并发传输多个 Stream。
> 
> 它减少了连接数量，提高了并发能力，但仍然受 TCP 丢包影响。

> [!example]- 多路复用  
> 浏览器同时请求 HTML、CSS、JS 和图片。
> 
> 在 HTTP/2 中，这些请求可以在同一个 TCP 连接中以多个 Stream 并发传输，每个帧带有 Stream ID，接收方按 ID 重新组装。

> [!warning]- 常见误区  
> HTTP/2 解决的是 HTTP 应用层的队头阻塞，但没有解决 TCP 层的队头阻塞。
> 
> 如果 TCP 连接中某个包丢失，后续字节即使到达，也必须等待丢失包重传后才能交给应用层。

> [!note]- 关键词  
> 二进制帧、Stream、Frame、Header Compression、多路复用、Server Push、TCP 队头阻塞

---

### 8.4 HTTP/3.0 的特点是什么？

> [!important]- 必须掌握  
> HTTP/3 是当前 HTTP 演进的重点。面试中常和 QUIC、UDP、连接迁移一起考。

> [!summary]- 核心结论  
> HTTP/3 放弃 TCP，基于 UDP 实现 QUIC。
> 
> QUIC 在应用层实现可靠传输、拥塞控制、TLS 集成、多路复用和连接迁移。

> [!example]- 移动端连接迁移  
> 手机从 Wi-Fi 切换到 4G 时，IP 地址可能变化。
> 
> TCP 连接依赖四元组识别连接，IP 变化后通常需要重连。
> 
> QUIC 使用 Connection ID 标识连接，只要上下文仍在，就可以快速迁移连接。

> [!warning]- 常见误区  
> HTTP/3 使用 UDP，不代表它不可靠。
> 
> QUIC 在 UDP 之上自己实现了可靠传输机制。

> [!note]- 关键词  
> HTTP/3、UDP、QUIC、0-RTT、Connection ID、连接迁移、无队头阻塞、TLS 1.3

## 9. QUIC 协议的概念和特点是什么？

> [!important]- 需要掌握  
> QUIC 是 HTTP/3 的核心。需要理解它为什么基于 UDP，以及它如何解决 TCP + TLS 的延迟和队头阻塞问题。

> [!summary]- 核心结论  
> QUIC 是基于 UDP 的传输协议，在应用层实现了类似 TCP 的可靠传输、拥塞控制、流量控制和连接管理。
> 
> QUIC 的核心优势包括无连接级队头阻塞、快速握手、连接迁移和内置 TLS 加密。

> [!question]- 面试怎么答  
> QUIC 是 HTTP/3 使用的传输协议，它基于 UDP，但在应用层实现了可靠传输。相比 TCP，QUIC 使用 Connection ID 标识连接，支持连接迁移；它将 TLS 集成到协议内部，减少握手 RTT；并且它的多个 Stream 之间相互独立，某个 Stream 丢包不会阻塞其他 Stream。
> 
> 所以 QUIC 的主要优势是降低连接建立延迟、改善多路复用下的队头阻塞，并提升移动网络切换时的连接稳定性。

> [!example]- QUIC 特点表
> 
> |特点|说明|解决的问题|
> |---|---|---|
> |基于 UDP|在 UDP 上实现可靠传输|避开 TCP 内核协议栈限制|
> |多路复用|一个连接中有多个独立 Stream|减少队头阻塞|
> |快速握手|QUIC 内置 TLS，通常 1-RTT，恢复时可 0-RTT|降低建连延迟|
> |连接迁移|使用 Connection ID，而不是只依赖 IP + 端口|移动端网络切换更稳定|
> |加密认证|大部分报文头认证，Body 加密|降低篡改和窃听风险|

> [!warning]- 常见误区  
> QUIC 不是简单地“HTTP 换成 UDP”。
> 
> 更准确地说，QUIC 是在 UDP 之上重新实现连接管理、可靠传输、拥塞控制和安全能力。

> [!note]- 关键词  
> UDP、QUIC、HTTP/3、Stream、Connection ID、0-RTT、1-RTT、TLS、连接迁移

## 10. QUIC 如何保证可靠传输？

> [!note]- 了解即可  
> 这个问题偏底层，面试中一般知道核心机制即可，不需要展开到完整协议细节。

> [!summary]- 核心结论  
> QUIC 通过递增的 Packet Number、Stream ID、Offset 和重传机制保证可靠传输。
> 
> Packet Number 用于确认和丢包检测；Stream ID 用于区分不同数据流；Offset 用于保证流内数据的顺序组装。

> [!example]- QUIC 可靠传输机制
> 
> |字段|作用|类比|
> |---|---|---|
> |Packet Number|标识每个 QUIC Packet，严格递增|用于 ACK 和丢包检测|
> |Stream ID|区分不同并发 Stream|类似多个独立请求通道|
> |Offset|标识 Stream 内数据位置|类似 TCP Seq|
> |Length|标识 Frame 数据长度|用于解析数据边界|

> [!question]- 面试怎么答  
> QUIC 基于 UDP，但它在应用层维护可靠性。每个 Packet 都有严格递增的 Packet Number，可以用于确认和丢包检测。一个 Packet 中可以包含多个 Frame，Stream Frame 中有 Stream ID、Offset 和 Length。
> 
> Stream ID 用于区分不同 HTTP 消息，Offset 用于保证同一个 Stream 内的数据能正确排序和重组。如果发生丢包，QUIC 可以根据这些信息重传对应的数据，而不会影响其他已经完整到达的 Stream。

> [!warning]- 常见误区  
> QUIC 的“无队头阻塞”不是说永远没有阻塞。
> 
> 如果某个 Stream 自己的数据丢包，这个 Stream 仍然需要等待重传；只是其他 Stream 不会被它阻塞。

## 11. HTTP 的 GET 和 POST 方法有什么区别？

> [!important]- 必须掌握  
> 这是 HTTP 基础高频题。必须能从语义、幂等性、参数位置、安全性和数据大小几个角度回答。

> [!summary]- 核心结论  
> GET 通常用于获取资源，POST 通常用于提交数据或修改资源。
> 
> GET 语义上是安全且幂等的；POST 通常不是幂等的，可能对服务器资源产生修改。

> [!question]- 面试怎么答  
> GET 一般用于从服务器获取资源，参数通常放在 URL 查询字符串中，因此会暴露在地址栏、浏览器历史和日志中。POST 一般用于提交数据，数据通常放在请求体中，适合提交表单、创建资源或修改服务器状态。
> 
> 从语义上说，GET 应该是安全和幂等的，不应该修改服务器资源；POST 通常不是幂等的，每次提交都可能产生新的影响。GET 受 URL 长度限制，POST 的请求体通常可以传更大的数据。

> [!example]- GET 和 POST 对比
> 
> |对比项|GET|POST|
> |---|---|---|
> |语义|获取资源|提交数据、创建或修改资源|
> |是否幂等|通常幂等|通常不幂等|
> |是否修改资源|不应修改|可能修改|
> |参数位置|通常在 URL 中|通常在 Body 中|
> |数据大小|受 URL 长度限制|通常限制更小，但由服务器配置决定|
> |安全性|参数更容易暴露|参数不在 URL 中，但不是加密|
> |缓存|更容易被缓存|默认不常缓存|
> |典型场景|查询文章、搜索关键词|登录、提交表单、创建订单|

> [!warning]- 常见误区  
> POST 不等于安全。POST 参数虽然不显示在 URL 中，但如果没有 HTTPS，仍然可能被抓包看到。
> 
> GET 和 POST 的本质区别首先是语义，不只是“参数放 URL 还是 Body”。

> [!note]- 关键词  
> 语义、安全、幂等、URL、Body、查询参数、请求体、资源修改

## 12. GET 请求可以带 Body 吗？

> [!important]- 需要掌握  
> 这是一个容易答错的细节题。关键是区分“协议规范没有绝对禁止”和“语义上不推荐”。

> [!summary]- 核心结论  
> RFC 规范并没有严格禁止 GET 请求携带 Body。
> 
> 但 GET 的语义是获取资源，通常通过 URL 查询参数表达条件，因此实践中不推荐给 GET 请求带 Body。

> [!question]- 面试怎么答  
> 从规范角度看，GET 请求并不是绝对不能带 Body，任何 HTTP 请求理论上都可以有消息体。
> 
> 但从语义和兼容性角度看，GET 用于获取资源，请求条件通常放在 URL 查询参数中。很多服务器、代理、缓存组件可能会忽略 GET 的 Body，所以实际开发中不建议依赖 GET Body 传参。

> [!example]- 正常 GET 查询
> 
> ```http
> GET /users?id=1001 HTTP/1.1
> Host: example.com
> ```
> 
> 查询条件放在 URL 中，更符合 GET 语义，也更容易被缓存系统识别。

> [!warning]- 常见误区  
> 不要简单回答“GET 绝对不能带 Body”。
> 
> 更准确的回答是：规范没有完全禁止，但语义上不需要，实践中兼容性差，所以不推荐使用。

> [!note]- 关键词  
> RFC、语义、兼容性、URL Query、Body、缓存、代理

## 13. 既然有 HTTP，为什么还要有 RPC？

> [!important]- 需要掌握  
> 这是后端和微服务面试常考题。重点不是说谁更高级，而是理解 HTTP 和 RPC 的定位不同。

> [!summary]- 核心结论  
> HTTP 是一个应用层协议；RPC 是远程过程调用思想，不一定绑定某一种具体协议。
> 
> HTTP 更常用于浏览器到服务器的 B/S 架构；RPC 更常用于服务内部的高性能 C/S 或微服务通信。

> [!question]- 面试怎么答  
> HTTP 和 RPC 都可以基于 TCP 实现，但定位不同。HTTP 是具体的应用层协议，最初主要服务于 Web 文本和资源传输；RPC 是一种远程调用方式，目标是让调用远程服务像调用本地函数一样。
> 
> 在公司内部微服务场景中，RPC 通常配合服务注册发现、长连接连接池和高效序列化协议，比如 Protobuf，传输体积更小、性能更好。而 HTTP 通用性更强，适合浏览器访问、开放 API 和跨平台场景。

> [!example]- HTTP 和 RPC 对比
> 
> |对比项|HTTP|RPC|
> |---|---|---|
> |本质|应用层协议|远程调用方式|
> |常见架构|B/S|C/S、微服务|
> |服务发现|DNS|Consul、Etcd、Redis、CoreDNS 等|
> |连接方式|Keep-Alive 长连接|长连接 + 连接池|
> |序列化|JSON 常见|Protobuf、Thrift 等|
> |可读性|较强|较弱|
> |性能|通用但冗余较多|定制化强，通常更高效|
> |典型场景|Web API、浏览器访问|内部服务调用|

> [!tip]- 为什么 RPC 性能通常更好？  
> HTTP + JSON 的 Header 和 Body 往往有较多冗余。
> 
> RPC 可以使用 Protobuf 这类二进制序列化协议，并且减少不必要的浏览器兼容逻辑，因此内部调用性能通常更好。

> [!warning]- 常见误区  
> RPC 不是某一个具体协议。
> 
> gRPC、Dubbo、Thrift 都可以看作 RPC 框架或协议实现。RPC 底层可以用 TCP，也可以基于 HTTP/2。

> [!note]- 关键词  
> HTTP、RPC、远程过程调用、B/S、C/S、微服务、服务发现、连接池、Protobuf、JSON、gRPC

## 14. 什么是 XSS 攻击？如何防范？

> [!important]- 需要掌握  
> XSS 是 Web 安全面试高频题。必须能解释攻击原理、常见类型和防御方式。

> [!summary]- 核心结论  
> XSS 是跨站脚本攻击，核心是攻击者把恶意脚本注入到网页中，让其他用户浏览页面时执行该脚本。
> 
> 根本原因是网站没有正确过滤、转义或限制用户输入和输出。

> [!question]- 面试怎么答  
> XSS 指攻击者利用网站对用户输入过滤不足的问题，把恶意 JavaScript 注入到页面中。当其他用户访问该页面时，脚本会在用户浏览器中执行，从而盗取 Cookie、冒充用户操作或篡改页面内容。
> 
> 防御 XSS 的核心是不要信任用户输入。服务端和前端都要进行输入校验、输出编码，过滤危险标签和事件属性，并给重要 Cookie 设置 `HttpOnly`，防止 JavaScript 读取 Cookie。

> [!example]- XSS 分类
> 
> |类型|说明|例子|
> |---|---|---|
> |反射型 XSS|恶意脚本通过 URL 参数传入，并立即反射到响应中|搜索框把关键词直接渲染到页面|
> |存储型 XSS|恶意脚本被存入数据库，用户访问页面时执行|留言板、评论区注入脚本|
> |DOM 型 XSS|前端 JavaScript 操作 DOM 时引入恶意内容|前端直接使用 `innerHTML` 渲染 URL 参数|

> [!example]- 常见危害
> 
> |危害|说明|
> |---|---|
> |窃取 Cookie|盗取登录态|
> |冒充用户操作|以用户身份发请求|
> |篡改页面|插入钓鱼链接或恶意内容|
> |窃取敏感数据|获取用户资料或企业数据|
> |网站挂马|引导用户下载恶意程序|

> [!example]- 防御方式
> 
> |防御方式|作用|
> |---|---|
> |输入校验|限制字段类型、长度和格式|
> |输出编码|将特殊字符转义为 HTML 实体|
> |过滤危险标签|移除 `<script>`、`<iframe>` 等|
> |过滤事件属性|移除 `onclick`、`onfocus` 等|
> |设置 `HttpOnly`|防止 JavaScript 读取 Cookie|
> |使用 CSP|限制页面可执行脚本来源|

> [!warning]- 常见误区  
> 只做前端校验不够，因为攻击者可以绕过浏览器直接发请求。
> 
> `HttpOnly` 不能阻止 XSS 发生，只能降低 Cookie 被盗的风险。

> [!note]- 关键词  
> XSS、脚本注入、输入校验、输出编码、HttpOnly、CSP、反射型、存储型、DOM 型

## 15. 什么是 CSRF 攻击？如何防范？

> [!important]- 需要掌握  
> CSRF 是 Web 安全高频题。重点理解它和 XSS 的区别：CSRF 是冒用用户身份发请求，XSS 是注入脚本。

> [!summary]- 核心结论  
> CSRF 是跨站请求伪造，攻击者诱导已登录用户访问恶意页面，利用浏览器自动携带 Cookie 的机制，向受信任网站发送伪造请求。
> 
> CSRF 的关键不是偷 Cookie，而是借用用户已经登录的状态。

> [!question]- 面试怎么答  
> CSRF 指用户登录网站 A 后，浏览器中保存了 A 的 Cookie。此时用户没有退出登录，又访问了恶意网站 B。B 构造一个请求发往网站 A，由于浏览器会自动携带 A 的 Cookie，网站 A 可能误以为这是用户本人发起的合法请求。
> 
> 防御 CSRF 的方式包括 CSRF Token、Referer 或 Origin 校验、SameSite Cookie，以及对关键操作增加二次验证。

> [!example]- CSRF 攻击流程
> 
> 1. 用户登录银行网站 A，浏览器保存登录 Cookie。
>     
> 2. 用户没有退出 A，又打开恶意网站 B。
>     
> 3. B 自动构造一个转账请求发给 A。
>     
> 4. 浏览器自动携带 A 的 Cookie。
>     
> 5. 如果 A 没有额外校验，就可能执行该请求。
>     

> [!example]- 防御方式
> 
> |防御方式|核心思想|
> |---|---|
> |CSRF Token|表单或请求头中携带随机 Token，服务端校验|
> |Referer 校验|检查请求来源页面是否可信|
> |Origin 校验|检查请求源站是否可信|
> |SameSite Cookie|限制跨站请求自动携带 Cookie|
> |二次验证|对转账、改密码等敏感操作再次确认|

> [!warning]- 常见误区  
> CSRF 不需要攻击者获取用户 Cookie。
> 
> 它利用的是浏览器会自动携带 Cookie 的机制。

> [!note]- 关键词  
> CSRF、跨站请求伪造、Cookie、Token、Referer、Origin、SameSite、二次验证

## 16. 什么是中间人攻击？如何防范？

> [!important]- 需要掌握  
> 中间人攻击是 HTTPS 和网络安全的重要背景题。需要能解释攻击者如何拦截通信，以及 HTTPS 为什么能缓解该问题。

> [!summary]- 核心结论  
> 中间人攻击指攻击者位于通信双方之间，分别与双方建立连接，并转发、监听或篡改数据。
> 
> 防范核心是身份认证、加密传输和证书校验。

> [!question]- 面试怎么答  
> 中间人攻击是指攻击者插入客户端和服务器之间，让客户端以为自己在和服务器通信，服务器也以为自己在和客户端通信，但实际上数据都经过攻击者转发。
> 
> 防范方式主要是使用 HTTPS，正确校验证书，禁用不安全的 SSL/TLS 版本，避免信任伪造证书。安全要求更高的场景可以使用双向 TLS 认证，让客户端和服务端互相验证身份。

> [!example]- 常见攻击方式
> 
> |攻击方式|说明|
> |---|---|
> |嗅探|捕获网络中传输的数据包|
> |数据包注入|向正常通信中插入恶意数据|
> |会话劫持|控制或复用用户会话|
> |SSL 剥离|将 HTTPS 降级为 HTTP，使通信变成明文|
> |伪造证书|给客户端返回攻击者自己的证书|

> [!example]- 防范方式
> 
> |防范方式|作用|
> |---|---|
> |使用 HTTPS|加密通信内容|
> |校验证书链|防止连接到伪造服务器|
> |禁用不安全 SSL/TLS|避免使用过时加密协议|
> |HSTS|强制浏览器使用 HTTPS|
> |双向 TLS 认证|客户端和服务端互相验证身份|
> |避免信任未知证书|防止伪造证书被接受|

> [!warning]- 常见误区  
> 只要用户主动接受伪造证书，HTTPS 的身份认证就会失效。
> 
> HTTPS 防的是通信被窃听和篡改，但前提是证书验证过程没有被破坏。

> [!note]- 关键词  
> 中间人攻击、嗅探、会话劫持、SSL 剥离、伪造证书、HTTPS、证书校验、HSTS、双向 TLS

## 17. 高频对比关系梳理

### 17.1 HTTP 与 HTTPS

|对比项|HTTP|HTTPS|
|---|---|---|
|安全性|明文|加密|
|身份认证|无|CA 证书|
|默认端口|80|443|
|连接过程|TCP 握手|TCP 握手 + TLS 握手|
|性能|较快|有加解密和握手开销|
|适合场景|非敏感资源|登录、支付、接口、安全通信|

---

### 17.2 强缓存与协商缓存

|对比项|强缓存|协商缓存|
|---|---|---|
|是否请求服务器|否|是|
|判断方|浏览器|服务器|
|常见状态码|无需状态码|304|
|常见字段|`Expires`、`Cache-Control`|`Last-Modified`、`ETag`|
|优点|最快，减少请求|保证资源新鲜度|
|缺点|资源变化感知弱|仍然需要一次请求|

---

### 17.3 HTTP/2 与 HTTP/3

|对比项|HTTP/2|HTTP/3|
|---|---|---|
|底层协议|TCP|UDP + QUIC|
|多路复用|支持|支持|
|队头阻塞|TCP 层仍存在|Stream 间基本消除|
|TLS|分层使用 TLS|QUIC 内置 TLS|
|连接迁移|不友好|支持 Connection ID|
|移动端表现|网络切换容易重连|网络切换更稳定|

---

### 17.4 XSS 与 CSRF

|对比项|XSS|CSRF|
|---|---|---|
|中文名|跨站脚本攻击|跨站请求伪造|
|攻击核心|注入并执行恶意脚本|冒用用户身份发请求|
|是否需要用户登录|不一定|通常需要|
|是否需要窃取 Cookie|可能会窃取|不需要|
|利用点|页面输入输出过滤不足|浏览器自动携带 Cookie|

## 18. 常见误区

> [!warning]- HTTP 常见误区
> 
> 1. HTTPS 不是新的应用层协议，而是 HTTP over TLS。
>     
> 2. HTTPS 不是绝对安全，证书信任链被破坏时仍可能被攻击。
>     
> 3. POST 不等于安全，没有 HTTPS 时 POST Body 也可能被抓包。
>     
> 4. GET 不是规范上绝对不能带 Body，而是语义和兼容性上不推荐。
>     
> 5. `304` 不是错误，而是协商缓存命中。
>     
> 6. HTTP/2 解决了应用层队头阻塞，但没有解决 TCP 层队头阻塞。
>     
> 7. HTTP/3 用 UDP 不代表不可靠，QUIC 自己实现了可靠传输。
>     
> 8. RPC 不是具体协议，而是一种远程调用方式。
>     
> 9. XSS 是脚本注入，CSRF 是伪造请求，两者攻击点不同。
>     
> 10. CSRF 不需要偷 Cookie，而是利用浏览器自动携带 Cookie。
>

## 19. 面试口述版答案

> [!question]- HTTP 和 HTTPS 区别  
> HTTP 是明文传输，默认端口 80，数据容易被窃听、篡改和冒充。HTTPS 是 HTTP over TLS，默认端口 443，通过证书验证服务端身份，并使用加密保证传输安全。HTTPS 相比 HTTP 多了 TLS 握手和加解密开销，但安全性更高。

> [!question]- HTTPS 握手过程  
> 客户端先发送 ClientHello，包含 TLS 版本、随机数和密码套件列表。服务端返回 ServerHello，确认版本和密码套件，并发送证书。客户端验证证书后，用服务端公钥加密 pre-master key 发送给服务端。双方根据随机数和 pre-master key 生成会话密钥，之后使用对称加密传输 HTTP 数据。

> [!question]- HTTP 状态码  
> HTTP 状态码分五类：1xx 是提示信息，2xx 是成功，3xx 是重定向或缓存，4xx 是客户端错误，5xx 是服务端错误。常见的有 200 成功，301 永久重定向，302 临时重定向，304 使用缓存，403 无权限，404 资源不存在，500 服务端错误，502 网关错误，503 服务不可用，504 网关超时。

> [!question]- HTTP 缓存  
> HTTP 缓存分强缓存和协商缓存。强缓存命中时浏览器直接使用本地缓存，不请求服务器，常见字段是 Expires 和 Cache-Control。协商缓存会请求服务器确认资源是否变化，如果没变化返回 304，浏览器继续使用缓存，常见字段是 Last-Modified 和 ETag。

> [!question]- HTTP 版本区别  
> HTTP/1.0 默认短连接，每次请求建连开销大。HTTP/1.1 默认长连接，支持管道化、缓存控制和 Range 断点续传。HTTP/2 使用二进制帧、多路复用、头部压缩和服务端推送，但仍受 TCP 丢包影响。HTTP/3 基于 UDP 和 QUIC，实现可靠传输、连接迁移和更好的多路复用，减少 TCP 队头阻塞问题。

> [!question]- GET 和 POST 区别  
> GET 通常用于获取资源，参数一般放在 URL 中，语义上安全且幂等。POST 通常用于提交数据或修改资源，参数一般放在请求体中，通常不幂等。GET 受 URL 长度限制，POST 更适合提交较大数据。但 POST 不是天然安全，只有配合 HTTPS 才能防止传输内容被窃听。

> [!question]- HTTP 和 RPC 区别  
> HTTP 是具体的应用层协议，RPC 是远程过程调用方式。HTTP 更适合浏览器访问和开放 API，通用性强；RPC 更常用于公司内部微服务调用，通常配合服务发现、连接池和 Protobuf 等高效序列化协议，性能和定制化能力更强。

> [!question]- XSS 和 CSRF 区别  
> XSS 是跨站脚本攻击，核心是攻击者向页面注入恶意脚本，让用户浏览器执行。CSRF 是跨站请求伪造，核心是诱导已登录用户发起伪造请求，利用浏览器自动携带 Cookie 的机制。XSS 防御重点是输入校验、输出编码、CSP 和 HttpOnly；CSRF 防御重点是 Token、Origin、Referer 和 SameSite Cookie。

## 21. 最终速记版

> [!tip]- HTTP 面试速记  
> HTTP 是明文，HTTPS 是 HTTP over TLS。
> 
> HTTPS 解决三件事：加密、认证、完整性。
> 
> TLS 握手核心：协商参数、验证证书、生成会话密钥、对称加密通信。
> 
> 状态码：`2xx` 成功，`3xx` 重定向或缓存，`4xx` 客户端错，`5xx` 服务端错。
> 
> 缓存：强缓存不请求服务器，协商缓存请求服务器，常见 `304`。
> 
> HTTP/1.1 解决连接复用，HTTP/2 解决应用层多路复用，HTTP/3 用 QUIC 解决 TCP 队头阻塞和连接迁移。
> 
> GET 获取资源，POST 提交数据；区别核心是语义，不只是参数位置。
> 
> RPC 是远程调用方式，常用于内部微服务，强调性能、服务发现和高效序列化。
> 
> XSS 是脚本注入，CSRF 是伪造请求，中间人攻击是拦截并控制通信双方连接。
