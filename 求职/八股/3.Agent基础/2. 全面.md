## 4. 高频问题整理

### 4.1 你这个算 workflow 还是 agent？

> [!important]- 必须掌握
> 面试第一问大概率是它——考你对"agent"这个被滥用的词有没有清醒定义，以及敢不敢诚实定位自己的项目。

> [!summary]- 核心结论
> 业界常用区分（Anthropic 的提法）：**workflow** 是用预定义代码路径编排 LLM 和工具；**agent** 是 LLM 自主决定步骤、工具与何时停止。二者是光谱不是二元。本项目完整版 = 单步 tool calling + 确定性组合层，靠近 workflow 端——这是刻意选择，不是做不到。

> [!question]- 面试怎么答
> "严格说它是一个 tool-calling workflow 而不是自主 agent：路由（无论规则还是 LLM）做的是单步工具选择，报告生成是确定性组合。我刻意不做多步自主规划，因为我的任务集是有限且明确的，自主性带来的是不可评测性而不是能力——先把单步做到可评测，是往多步走的前提。"

> [!warning]- 常见误区
> 把 demo 吹成"自主 agent"——追问一句"它自己决定过调用顺序吗"就露馅。反方向也错：不要因此贬低项目，"知道什么时候不需要 agent"本身就是 agent 工程能力。

> [!note]- 关键词
> workflow vs agent 光谱、预定义路径、自主规划、单步 tool calling、刻意取舍

### 4.2 Function calling 的进阶细节（多轮、并行、tool_choice、报错）

> [!important]- 必须掌握
> 基础时序（声明 schema → 模型出 tool_use → 运行时执行 → 结果喂回）见 [[Agent 基础：从关键词路由到 Function Calling]]；面试深挖的是下面四个边角。

> [!summary]- 核心结论
> ① 多轮 loop 的终止条件：模型不再请求工具（stop_reason 从 tool_use 变回正常结束）或达到轮数上限；② 模型可以**一次请求多个工具**（并行 tool calls），运行时可并发执行；③ tool_choice 参数控制强制程度：自动选 / 必须选一个 / 指定某个 / 禁用；④ 工具报错不要吞掉——把错误信息作为 tool result 喂回去，模型会自己调整参数重试或换说法。

> [!example]- 具体例子
> 项目 W2 计划：DeepSeek/Qwen 走 OpenAI 兼容协议（tool_calls / role 为 tool 的消息），Claude 协议是 tool_use / tool_result 内容块——形状同构，换供应商只改适配层。`compare_modes` 返回 `found: False` 时，这个 dict 原样作为 tool result 喂回模型，模型自然渲染"数据不足"的中文回答——**工具的明确失败让 LLM 的兜底变成免费的**。

> [!warning]- 常见误区
> "循环是模型控制的" ❌——while 循环写在你的代码里，模型只是每轮产出"继续调工具"或"给出答案"的信号；轮数上限、超时、预算控制全是你的责任。

> [!note]- 关键词
> stop_reason、多轮终止、并行 tool calls、tool_choice、错误作为 tool result 回传、OpenAI 兼容协议

### 4.3 好的 tool 应该怎么设计？

> [!important]- 必须掌握
> 你的项目在这题上例子最全，是最该主动引导过去的领地。

> [!summary]- 核心结论
> 六条原则，条条有项目实例：①**结构化输出**（dict 而非文案，形状稳定 = 合同）；②**明确失败**（`found: False` + message，宁可失败不含糊成功）；③**全精度输出**（舍入是渲染层的事）；④**只读/幂等**（重试和并行天然安全）；⑤**描述即路由**（tool description 决定 LLM 选不选它，写描述 = 写路由规则）；⑥**自己校验参数**（LLM 产出的参数不可信，schema 校验 + 快速失败）。

> [!question]- 面试怎么答
> "我的每个 tool 返回统一形状的 dict：found 标志 + 数据或 message。这样上层不需要区分'哪种失败'，LLM 也能直接把失败渲染成得体回答。数值保留全精度、舍入放渲染层，因为 tool 的消费者不只有人，还有下游计算和评测脚本。所有工具只读 SQLite，幂等，这让将来 LLM 重试调用零风险。"

> [!warning]- 常见误区
> "参数校验交给 LLM 保证" ❌——模型产出的 JSON 可能缺字段、类型错、值越界，运行时必须自己校验；"工具越强大越好" ❌——工具边界越窄语义越清晰，`compare_modes` 拒绝单边返回就是窄合同的价值。

> [!note]- 关键词
> 结构化输出、明确失败、全精度、幂等只读、description engineering、参数校验、最小合同

### 4.4 多工具编排（orchestration）有哪几档？

> [!info]- 需要掌握
> 从你已实现的东西到 ReAct 的进阶路线，展示"知道往哪扩展"。

> [!summary]- 核心结论
> 三档：①**单发路由**——一问选一个工具（router 现状）；②**固定编排**——代码写死调用顺序和汇总逻辑（`scaling_report`：三工具 → 六节报告，手写 orchestration）；③**动态规划**——LLM 每轮看结果决定下一步（ReAct：推理和行动交替；plan-and-execute：先出完整计划再逐步执行）。档位越高表达力越强、可测性越差。

> [!example]- 具体例子
> `scaling_report` 干的事（调多个工具 → 拿结构化结果 → 汇总成自然语言）正是 LLM agent loop 每一轮的形状——W2 把"决策者"从代码换成 LLM 时，工具层一行不改。这就是"先手写编排再上 LLM"的路线价值。

> [!note]- 关键词
> 单发路由、固定编排、ReAct、plan-and-execute、决策者可替换

### 4.5 Agent 的"记忆"分几种？

> [!info]- 需要掌握
> "你的 agent 有记忆吗"是高频问法，答案藏在项目名里（benchmark memory）。

> [!summary]- 核心结论
> 三类：①**短期记忆** = 对话上下文窗口，会话结束即失；②**长期结构化记忆** = 外部数据库，精确查询——SQLite `benchmark_runs` 就是它，用 SQL 而不是语义检索访问；③**长期非结构化记忆** = 文档库 + 语义检索（RAG），W3 的 HPC 笔记入库。上下文塞不下的、要跨会话的、要精确聚合的，都必须外置。

> [!warning]- 常见误区
> "把历史都塞进 prompt 就是记忆" ❌——上下文有限且贵，长对话需要压缩/摘要（compaction，了解即可）；"RAG 是唯一的长期记忆" ❌——结构化数据用数据库精确查询远优于语义检索，你的项目就是证据。

> [!note]- 关键词
> 上下文窗口、外置记忆、结构化 vs 非结构化、SQL 精确查询 vs 语义检索

### 4.6 RAG 的完整机制

> [!important]- 必须掌握
> Agent 岗必考。W3 只做"最小可讲"，但机制要能完整讲。

> [!summary]- 核心结论
> RAG（Retrieval-Augmented Generation）= 回答前先从文档库**检索**相关片段塞进上下文，让模型基于真材料生成。离线阶段：文档 → 切块（chunking）→ 向量化（embedding）→ 存向量库。在线阶段：问题向量化 → 相似度检索 top-k → 拼进 prompt → 生成（最好带引用）。

> [!example]- 具体例子
> 机制细节：embedding 模型把文本映射为高维向量，语义相近则距离近（常用余弦相似度）；chunk 一般几百 token、留 10–20% 重叠防止句子被切断；top-k 取 3–5 个。W3 计划：个人 HPC 笔记入库，问"ARCHER2 的 NUMA 结构"时检索笔记原文作答——benchmark 数字仍走 SQL 工具，**RAG 只管非结构化知识**。

> [!question]- 面试怎么答
> 对比题标准答案：**RAG vs 微调 vs 长上下文**——RAG 改知识只需更新文档库、可溯源、成本低，适合常变的事实性知识；微调改的是行为风格而非注入事实，且不可溯源；长上下文塞全部文档贵且检索精度随长度衰减。三者互补不互斥。另一个统一视角：**RAG 本质是给 agent 的一个检索 tool**——和 SQL 工具并列，路由器决定这问题查库还是查笔记。

> [!warning]- 常见误区
> "RAG 就是数据库查询" ❌——语义检索按相似度模糊命中，SQL 按条件精确命中，各管一类数据；"有了长上下文 RAG 就死了" ❌——成本、延迟、可溯源性三个维度都还站在 RAG 一边；"检索到 = 答对" ❌——检索质量（切块、embedding 选型）才是 RAG 效果的瓶颈。

> [!note]- 关键词
> chunking、embedding、余弦相似度、top-k、引用溯源、hybrid 检索（BM25+向量，了解）、rerank（了解）、RAG 是一种 tool

### 4.7 评测（evals）怎么做？

> [!important]- 必须掌握
> "全程可评测"是这个项目的核心卖点，这题必须答成主场。

> [!summary]- 核心结论
> 概率系统不评测 = 质量不可声称。W2 计划：30–50 题中文评测集，同一套题分别跑规则 router 和 LLM router，对比 intent 准确率和 slot 抽取准确率。评测集构成要覆盖四类：常规问法、改写/口语变体、边界（缺参数、多意图混杂）、应当 fallback 的域外问题。

> [!question]- 面试怎么答
> "我的评测有两级基准。路由级：每题标注期望的 intent 和参数，程序化比对，得到两种 router 的准确率对照表。生成级（报告/解读这类自由文本）：确定性规则版就是 **golden reference**——推荐配置、阈值触发位置、归因方向都有唯一可验证的正确值，LLM 版按事实点覆盖打分。纯开放文本才需要 LLM-as-judge，给评分模型一个 rubric 逐条打分，但它自身也有偏差，所以能程序化的绝不上 judge。"

> [!warning]- 常见误区
> "temperature = 0 就是确定性" ❌——采样确定不等于系统确定：服务端实现、浮点并行归约、模型版本更新都会让输出漂移，所以评测要看**通过率的分布**而不是单次结果；"评测集 = 测试用例" 半对——评测衡量概率系统的统计质量（准确率），测试断言确定系统的正确性（过/不过），两套机制并存正是项目双 router 架构的镜像。

> [!note]- 关键词
> 评测集构建四象限、intent/slot 准确率、golden reference、LLM-as-judge、rubric、回归评测（改 prompt 重跑全集）

### 4.8 幻觉与 grounding

> [!important]- 必须掌握
> 批判层核心题："LLM 会胡编，你怎么办？"

> [!summary]- 核心结论
> 幻觉的机制成因：模型逐 token 取最大似然，生成过程**没有真值校验环节**，流畅度和真实性是两个不相关的量。Grounding = 强制回答锚定在外部真实数据上：先调工具查库，再让模型基于返回结果作答——模型的角色从"知识来源"降级为"语言接口"。

> [!example]- 具体例子
> 项目就是一个 grounding 案例：问"100 万规模最快配置"，不让模型回忆（它根本没见过你的 ARCHER2 数据，只能编一个像样的），而是 `best_config` 查 SQLite 返回 `ranks=128, time=3.866`，模型只负责把 dict 说成人话。查无数据时返回 found: False，对应的回答是"没有这个数据"而不是编一个——**明确失败是 grounding 的一部分**。

> [!warning]- 常见误区
> "把幻觉 prompt 掉" ❌——提示词能降频率，机制上无法消除；可靠路径是架构性的：工具查询 + 引用 + 允许说不知道 + 评测把关。

> [!note]- 关键词
> 最大似然无真值校验、grounding、模型是语言接口不是知识源、拒答设计、引用

### 4.9 可靠性工程：失败怎么兜？

> [!info]- 需要掌握
> task_008 Q1 的通用化：一条链路上每层的失败策略。

> [!summary]- 核心结论
> 四件套：①**明确失败**——工具层 found: False，绝不静默降级；②**优雅降级**——组合层缺一角照常出产物（报告"数据不足"节）；③**重试与幂等**——只读工具天然幂等，重试零风险；有副作用的操作要先设计幂等键再谈重试；④**兜底 fallback**——LLM 挂了/超时/超预算时退回规则 router，规则层永远在线（混合路由的第二重价值）。

> [!question]- 面试怎么答
> "我的失败策略分层：工具诚实失败，组合层决定降级还是透传，入口层永远有确定性兜底。关键认知是**下层的明确失败是上层能优雅降级的前提**——如果 compare_modes 缺数据时含糊地返回单边结果，报告层根本不知道该降级。"

> [!note]- 关键词
> 明确失败、优雅降级、幂等、重试、fallback 链、超时预算

### 4.10 可观测性：TraceID 与结构化日志

> [!info]- 需要掌握
> W3 内容。"你的 agent 答错了一次，你怎么查？"

> [!summary]- 核心结论
> Agent 是多步 + 概率系统，出错后**唯一的复盘手段是日志**。两件事：①**结构化日志**——JSON 行而非 print，字段可查询可聚合；②**TraceID**——每个请求生成唯一 ID，随调用链透传（router → tool → LLM 调用 → 渲染），一个 ID 拉出一次请求的完整轨迹。记录内容：输入、路由决策（命中哪条规则/模型选了哪个 tool）、每次 tool 调用的参数和耗时、LLM 的 token 数与成本、最终输出。

> [!example]- 具体例子
> 排障流程：用户报"答非所问"→ 拿 TraceID 查日志 → 一眼定位是路由错（intent 选错）、解析错（unknowns 抽错）、tool 错（SQL 无结果）还是渲染错——四层各有日志字段，不用复现就能归因。这也是评测集素材来源：错误案例直接进评测集防回归。

> [!note]- 关键词
> TraceID 全链路透传、结构化 JSON 日志、成本与延迟记录、错误案例回流评测集

### 4.11 服务化：FastAPI 为什么是"薄"封装？

> [!info]- 需要掌握
> W3 内容。考分层意识，不考 FastAPI 本身。

> [!summary]- 核心结论
> "薄"= 业务逻辑全部留在 tools/router/report 层，HTTP 只是**与 CLI 平级的另一个入口**：解析请求 → 调同一批函数 → 返回 JSON。收益：CLI 和 API 行为逐字一致（同一套测试保障）、pydantic 请求校验恰好是 tool schema 的 HTTP 版、无状态设计（每个请求独立，方便水平扩展）。流式响应（SSE）了解即可：LLM 逐 token 返回时提升体感，确定性工具不需要。

> [!warning]- 常见误区
> 把业务写进路由函数里——CLI 和 API 开始行为分叉，测试只能覆盖一边。判断标准：砍掉 FastAPI，项目功能应一点不少。

> [!note]- 关键词
> 薄封装、入口层平级、pydantic 校验、无状态、SSE（了解）

### 4.12 安全：prompt injection 与密钥管理

> [!info]- 需要掌握
> 应届生主动谈安全就是加分项，两分钟版本足够。

> [!summary]- 核心结论
> **Prompt injection** = 外部数据里混入的指令被模型当成命令执行。注入面不只是用户输入：**tool 返回值和 RAG 检索出的文档**都会进上下文——W3 笔记入库后，笔记里一句"忽略之前的指令"理论上就是注入。缓解：数据与指令分离（外部内容标记为数据）、**最小权限**（工具只读 SQLite，注入成功也无法写库删库）、输出校验。**密钥管理**：key 走环境变量，永不入库（项目 Never 条款），公开样例脱敏路径。

> [!question]- 面试怎么答
> "我的注入面评估：工具全部只读、无 shell 执行、无网络侧写操作，最坏情况是答错不是被劫持——但 W3 引入 RAG 后笔记内容成为新注入面，需要把检索结果明确标记为引用数据而不是指令。"能主动做这个评估本身就是答案。

> [!note]- 关键词
> 注入面（用户输入/tool 结果/RAG 文档）、数据指令分离、最小权限、只读工具、key 不入库

### 4.13 生态名词速览

> [!note]- 了解即可
> 每个一句话，说得清"是什么 + 我为什么没用"即可，不需要深入。
> - **LangChain**：LLM 应用的组件封装库（链、工具、记忆）。不用：抽象层遮住机制，学习期直接写裸 API 每层可讲。
> - **LangGraph**：把 agent 编排成显式状态图，管多步/分支/回退。不用：单步路由 + 固定组合还不需要图。
> - **MCP（Model Context Protocol）**：把工具/数据源接口标准化的开放协议（类比"工具的 USB-C"），host 连 server 即获得其工具。不用但要会说：我的 tools 层形状（name + 参数 + 结构化返回）与 MCP tool 同构，迁移是包装问题。
> - **Multi-agent**：多个 LLM 角色协作（规划者/执行者/评审者）。不用：单 agent 单步都没评测清楚前，多 agent 是复杂度不是能力。
> - 统一话术："这是刻意的减法——每一层我都要能白板重写，框架等到规模需要时再上。"

## 5. 完整版请求生命周期（流程梳理）

一次中文提问在完整版系统里的旅程，每步对应一个可指认的模块：

```
用户中文问题
   │  FastAPI 入口（W3）：pydantic 校验，生成 TraceID
   ▼
路由层：规则 router 先试（毫秒、免费、可测）
   │        └─ 未命中 → LLM function calling 兜长尾（W2）
   ▼      （两层共享同一 intent/tool 接口）
工具层：best_config / compare_modes / scaling_summary → SQLite（结构化记忆）
   │        └─ 概念性问题 → RAG 检索 HPC 笔记（W3，非结构化记忆）
   ▼
组合/渲染层：单答案直接渲染；报告走 scaling_report 六节组装
   │
   ▼
结构化日志落盘（TraceID 串全链路）→ 中文回答 / Markdown 报告
   │
   └─ 错误案例回流 → 评测集（W2）→ 回归防护
```

面试可以直接画这张图——每个箭头都能停下来深挖，而你每层都有实现或明确设计。

## 6. 常见误区（汇总表）

| 误区 | 正确认知 |
|---|---|
| "LLM 调用了函数" | LLM 只产出调用请求 JSON，执行永远在你的运行时 |
| "agent loop 由模型控制" | while 循环、轮数上限、预算全在你的代码里 |
| "temperature = 0 即确定性" | 采样确定 ≠ 系统确定；服务端与版本都会漂移 |
| "RAG 就是查数据库" | 语义模糊命中 vs SQL 精确命中，各管一类数据 |
| "长上下文淘汰 RAG" | 成本、延迟、可溯源三个维度 RAG 仍占优 |
| "幻觉可以被 prompt 消除" | 只能降频；可靠性要靠 grounding + 评测的架构解 |
| "评测 = 跑通 demo" | 评测是带标注答案的统计度量，demo 是单点样本 |
| "工具越强大越好" | 窄合同语义清晰；宁可明确失败不要含糊成功 |
| "把项目叫自主 agent 显得厉害" | 一句"它自己决定过调用顺序吗"就塌；诚实定位反而是能力 |

## 7. 面试口述版答案

**60 秒项目叙事（背熟）**：

> 我把真实 ARCHER2 上的 PETSc benchmark 数据结构化成 SQLite benchmark memory，把性能分析任务封装成一组确定性 tools——结构化返回、明确失败、全精度输出；先用中文规则 router 做了一个可验证的 baseline，再接 LLM function calling，两种 router 共享同一套工具接口，最后用自建中文评测集对比两者的路由准确率。"先确定性基线、再上 LLM、全程可评测"是刻意设计：确定性版本既是 fallback，也是评测 LLM 版本的 golden reference。

**三个高频追问的接法**：

- *"为什么不直接上 LLM？"* → 规则版给了三样东西：零成本可复测的 baseline、LLM 挂掉时的 fallback、评测 LLM 的参照系。不是不会用 LLM，是先让 LLM 的收益可度量。
- *"你的 agent 和 ChatGPT 套壳有什么区别？"* → Grounding：回答全部锚定在工具查询的真实数据上，查无数据明确说没有；套壳的答案来自模型记忆，我的答案来自我的数据。
- *"接下来怎么扩展？"* → 按已有设计说 W2/W3（评测集 → RAG → 可观测性），每项都说"设计是……还没实现"——红线：**不声称未实现的模块**。

## 9. 最终速记版

1. Workflow 用代码编排，agent 让模型决定步骤——我的项目是前者，刻意的。
2. LLM 只产出调用请求，执行、校验、循环控制全在我的运行时。
3. 好工具 = 结构化输出 + 明确失败 + 全精度 + 幂等 + 好描述 + 自校验。
4. 记忆三分：上下文（短）、SQLite（长·结构化）、RAG（长·非结构化）。
5. RAG = 切块 → 向量化 → 检索 top-k → 拼 prompt → 带引用生成。
6. 评测：路由级程序化比对，生成级拿确定性规则当 golden reference。
7. 幻觉是机制问题，解法是架构（grounding + 拒答 + 评测），不是 prompt。
8. 下层明确失败，上层才能优雅降级；规则层是永远在线的 fallback。
9. TraceID 串全链路，错误案例回流评测集。
10. 红线：只声称已实现的；"知道什么时候不用 agent/框架"本身就是答案。
