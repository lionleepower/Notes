# Agent 基础：从关键词路由到 Function Calling

> [!info] 这篇笔记为什么存在
> 项目里的 `router.py` 是一个"无 LLM 的 agent loop v0"。
> 面试官会顺着它追问：这和真正的 LLM agent / function calling 是什么关系？
> 本笔记只讲通用概念；project 里的 Q1/Q3/Q5 要用自己的话连回来。

## 1. Agent loop 是什么

一个 agent 的最小循环（不管有没有 LLM）：

```
感知输入 → 决策（选哪个动作/工具 + 带什么参数） → 执行 → 观察结果 → 产出回应（或继续循环）
```

LLM agent 只是把其中 **"决策"** 这一步交给了模型：

```
用户消息 → LLM 决定调哪个 tool、传什么参数 → 运行时执行 tool
        → tool 结果喂回 LLM → LLM 决定：再调一个 tool？还是渲染最终回答？
```

关键认知：**loop 的骨架和 tool 层是固定的，可替换的只是"决策者"**。
决策者可以是一张关键词表（确定性），也可以是 LLM（概率性）。

## 2. Intent 与 Slot（经典对话系统的两个词）

LLM 之前的对话系统（Siri、客服机器人）就靠这两件事运转：

- **Intent classification（意图分类）**：这句话想干什么？
  → "查运费" / "查天气" / "订闹钟"，各对应一个处理器。
- **Slot filling（槽位填充）**：执行这个意图缺哪些参数？
  → 查天气需要 `city`；订闹钟需要 `time`。

两个配套概念：

- **Ask-back / clarification（反问补槽）**：intent 明确但 slot 缺失时，
  不报错，而是反问用户（"请问查哪个城市？"）。
- **Fallback intent（兜底意图）**：什么都没命中时的 `unknown`，
  给一句"我目前能回答哪些问题"，而不是硬猜。

> [!tip] 一句话对上号
> 意图分类器输出 intent，槽位抽取器输出参数，二者合起来就是一次"结构化的动作请求"。
> 这个形状在 LLM 时代没有变，变的只是谁来产出它（见下一节）。

## 3. Function calling / Tool use：LLM 时代的同一件事

Function calling 的完整机制（以 Claude API 为例，OpenAI 同构）：

**① 你先声明工具清单（tool schema）**——每个工具 = 名字 + 描述 + 参数的 JSON Schema：

```json
{
  "name": "get_weather",
  "description": "Get current weather for a city. Use when the user asks about weather.",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "City name, e.g. 'Beijing'"}
    },
    "required": ["city"]
  }
}
```

**② 模型不执行任何东西**，它只输出一个结构化请求：

```json
{"type": "tool_use", "name": "get_weather", "input": {"city": "Beijing"}}
```

**③ 你的运行时**负责真正执行函数，把结果作为 `tool_result` 消息喂回去；
**④ 模型**拿到结果后渲染自然语言回答（或继续调下一个工具）。

> [!important] 最容易被面试官抓的误解
> "LLM 调用了函数" ❌ —— LLM 只**产出调用请求**（name + arguments 的 JSON），
> 执行永远发生在你的代码里。所以 tool 层必须自己校验参数、自己处理"查无数据"。

对应关系表（背下来）：

| 经典对话系统 | Function calling | 本质 |
|---|---|---|
| intent | tool name | 选哪个动作 |
| slots | tool arguments (JSON) | 带什么参数 |
| 意图分类器（规则/小模型） | LLM + tool schema 里的 description | 谁来决策 |
| ask-back 反问 | 模型自然生成追问，或 schema 校验失败后追问 | 缺参数怎么办 |
| fallback intent | 模型不调 tool、直接回复"做不到" | 兜底 |

## 4. 确定性路由 vs LLM 路由：取舍

| 维度 | 关键词/规则路由 | LLM function calling |
|---|---|---|
| 确定性 | 同一输入永远同一输出 | 概率采样，可能漂移 |
| 可测试性 | 断言能钉死，测试零依赖 | 得 mock API 或接受不稳定断言 |
| 运行环境 | 离线、零成本、毫秒级 | 要网络、要 key、有延迟和账单 |
| 表达力 | 只认写过的模式，改写就漏 | 任意措辞、多语言、错别字都能接 |
| 扩展成本 | intent 一多，规则互相打架 | 加一个 tool schema 即可 |
| 可解释性 | 每次路由都能指出命中哪条规则 | 只能事后看模型"想了什么" |

什么时候**必须**换 LLM：
- 用户措辞开放（无法穷举关键词）；
- intent 数量多且语义相近（规则开始误伤）；
- 需要多轮上下文（"那 50 万呢？"——省略主语，规则接不住）；
- 需要一次组合多个工具（plan 而不是单发路由）。

工程上常见的**混合策略**：规则先兜住高频/高确定性的问法（快、免费、可测），
LLM 只处理规则漏掉的长尾——两层共享同一个 intent/tool 接口。

## 5. 这些词面试里还会出现

- **ReAct**：Reason + Act 交替的 prompt 范式，agent loop 的经典形态。
- **Grounding**：回答必须锚定在 tool 返回的真实数据上，而不是模型编造——
  这也是"先查库再回答"比"让模型直接答"可靠的原因。
- **Deterministic / reproducible**：同输入同输出；demo、测试、debug 都靠它。
- **Tool schema 的 description 就是 prompt**：LLM 靠读 description 决定调不调，
  写工具描述 = 写路由规则，只是从正则换成了自然语言。
- **Structured output**：让模型输出严格 JSON（intent dict 就是它的手写版）。
